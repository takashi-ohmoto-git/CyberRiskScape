# 脅威モデルを AI が読める Security Context に変換する

[English](security-context.md) | **日本語**

AI はコードを読んで脆弱性を探せます。では、なぜ人間が図を描くのでしょうか。

**コードには書かれていないことがあるからです。** どこに信頼境界を引いたか、何を守りたいか、
どのリスクを受け入れると決めたか、何を調べなくてよいと判断したか — これらはリポジトリを
いくら読んでも出てきません。**人間が決めたこと**だからです。

この章では、ここまでの章で作った脅威モデルを **Markdown として書き出し、AI による脆弱性診断の
入力として使う**手順を説明します。CyberRiskScape は脅威を並べるだけのツールではなく、
**人間が与えた前提を AI が読める形式に変換する層**として使えます。

この章は、ここまでの章で記録した内容 — とくに
[Analytics でリスクを評価する](analytics-assessment.ja.md) で付けたリスク評価と対応方針 — を
前提にします。題材は [はじめての脅威モデル](first-threat-model.ja.md) で作った
**AI チャットボットの図**のままです（ユーザー ⇄ Front-end Server ⇄ LLM ⇄ RAG ⇄ データストア、脅威 48 件）。

---

## 1. 全体の流れ

```
  CyberRiskScape で作図・評価
            │
            ↓  Report → DCRH THREAT_MODEL.md
      THREAT_MODEL.md
            │
            ↓  解析対象のリポジトリへ置く
    AI による脆弱性診断
   （スキャン → トリアージ → 修正）
            │
            ↓
       人間による検証
```

**AI と競合しません。AI の入力品質を決める側に立ちます。**

---

## 2. 手順 ① — 書き出す前に整えておく

出力の質は、**書き出す前にどれだけ記録したか**でほぼ決まります。
最低限、次の 3 つを済ませてから出力してください。どれも
[Analytics でリスクを評価する](analytics-assessment.ja.md) で説明した操作です。

| 記録しておくもの | 出力のどこに効くか |
|---|---|
| **リスク評価**（Impact × Likelihood） | 脅威表の `impact` / `likelihood` 列。未評価だと既定値になる |
| **リスク対応方針**（回避／低減／移転／受容／誤検知） | `status` 列と、Deprioritized セクション |
| **対策実装状況**（実装済み／対策対象外 等） | `status` 列。実装済みだけが `mitigated` に格上げされる |

**特にリスク評価は効きます。** ルール由来の severity は一般論ですが、リスク評価を付けると
**あなたの文脈での評価**が出力されます。AI 側はこれを基準に指摘の重み付けを変えられます。

また、出力対象は**いま画面に表示している脅威一覧**です。深度レイヤーとフレームワークタブの
絞り込みがそのまま効くので、**特定の観点だけを切り出したいときは先にタブを切り替えてください。**

---

## 3. 手順 ② — Markdown で書き出す

左サイドバーの **Report** を開き、**「DCRH THREAT_MODEL.md（Anthropic 公式互換）」**を選びます。

![Report メニュー](../assets/guide/threat-panel/07-report.png)

`threat-report_<システム名>_<レイヤー>_<日付>.md` という名前でダウンロードされます。

この Markdown は、Anthropic が公開している OSS のリファレンス実装
[`defending-code-reference-harness`](https://github.com/anthropics/defending-code-reference-harness)
が使う `THREAT_MODEL.md` と同じ構造です。見出し・列名・列の値は**下流のツールとの取り決め**に
なっているため、**中身を手で書き換えるときは構造を崩さないよう注意してください。**

> 同じメニューにある CSV / JSON は用途が違います。CSV は表計算ソフトでの仕分けと共有、
> JSON は他ツールへの取り込み。**AI に読ませるなら Markdown** です。

---

## 4. 手順 ③ — 中身を確認する

開くと 8 つのセクションが並んでいます。**渡す前に、最低でも 1・5・6 は目を通してください。**

| セクション | 中身 | 由来 |
|---|---|---|
| `## 1. System context` | 何を作っているかの散文 | プロジェクト情報（目的・ビジネスインパクト・セキュリティ目標） |
| `## 2. Assets` | 資産の表 | 図のコンポーネントと境界 |
| `## 3. Entry points & trust boundaries` | 入口と信頼境界の表 | 脅威が紐づくデータフロー |
| `## 4. Threats` | **脅威の表（本体）** | 脅威一覧 |
| `## 5. Deprioritized` | **対象外にしたものと、その理由** | 誤検知／対策対象外／リスク受容 |
| `## 6. Open questions` | **埋められなかった項目の明示** | 変換の限界（§7 参照） |
| `## 7. Provenance` | 出所（ツール名・日付・対象） | — |
| `## 8. Recommended mitigations` | 緩和策と対象脅威 ID | 緩和策 |

脅威表の列はこうなっています。

```
| id | threat | actor | surface | asset | impact | likelihood | status | controls | evidence |
```

`id` は出力の中だけで振り直される連番（`T1`, `T2`, …）です。ファイル末尾のコメントに
CyberRiskScape 側の脅威 ID との対応表が入っているので、**指摘が返ってきたときに元の脅威へ
たどり着けます。**

### 記録した内容がどう変換されるか

| あなたが記録したこと | `status` 列 | 備考 |
|---|---|---|
| 対策実装状況＝**実装済み** | `mitigated` | **実装済みのときだけ**格上げされます |
| 対応方針＝回避／低減／移転 | `partially_mitigated` | 理由のメモは `controls` 列に併記 |
| 対応方針＝**リスク受容** | `risk_accepted` | Deprioritized にも理由つきで載ります |
| 対応方針＝**誤検知** | （脅威表から除外） | Deprioritized にのみ理由つきで載ります |
| 対策実装状況＝**対策対象外** | （脅威表から除外） | 同上 |
| 何も記録していない | `unmitigated` | — |

**「一覧から消えること」と「記録から消えること」は別です。** 誤検知にした脅威も、
**なぜ誤検知と判断したかという理由つきで**出力されます。これは後述のとおり、
AI に「これは追わなくてよい」と伝えるための情報です。

リスク評価は `impact` と `likelihood` の 2 列になります。`impact` は実効 severity
（評価済みならあなたの評価、未評価ならルール由来）、`likelihood` は再現性と攻撃容易性の
評価から 5 段階（`very_rare` / `rare` / `possible` / `likely` / `almost_certain`）へ対応します。
**未評価の脅威は `possible` が既定値になり、その事実は Open questions に明記されます。**

## 5. 手順 ④ — AI の入力として使う

### 公式ハーネスで使う場合

`defending-code-reference-harness` は、脅威モデルを起点にした一連のスキルを持っています。

| スキル | 役割 |
|---|---|
| `/threat-model` | 脅威モデルを作る（**ここを CyberRiskScape で置き換えます**） |
| `/vuln-scan` | 静的な脆弱性スキャン |
| `/triage` | 検出結果の検証・重複排除・順位付け |
| `/patch` | 修正の生成と検証 |

手順は次のとおりです。

1. ダウンロードしたファイルを **`THREAT_MODEL.md`** にリネームする
2. **解析対象のディレクトリ直下**（ハーネスに渡すディレクトリ）に置く
3. `/threat-model` を実行せず、そのまま `/vuln-scan` → `/triage` → `/patch` へ進む

つまり **`/threat-model` の出力を、人間が検証した脅威モデルで差し替える**使い方です。

### 公式ハーネス以外で使う場合

出力は素の Markdown なので、**任意の AI アシスタントにそのまま読ませられます。**
ただし正確に言うと、**この形式を前提として消費する仕組みを持っているのは公式ハーネス**で、
それ以外は「Markdown として読める」という意味です。過度な期待はしないでください。

手軽に使うなら、コードと一緒に渡してこう依頼するのが分かりやすい形です。

```
添付の THREAT_MODEL.md は、このシステムについて人間が作成・検証した脅威モデルです。
- section 4 の脅威を、実際のコードに対応する箇所があるか確認してください
- section 5 に載っているものは検討済みです。調査対象から外してください
- section 6 に書かれている未確定事項には触れないでください
```

## 6. なぜ効くのか

### ① 誤検知が減る

公式ハーネスは、**脅威モデルを「誤検知を減らすためのスコープ定義」として位置づけています。**
AI にリポジトリだけを渡すと、そのシステムでは起こり得ない指摘まで出てきます。
「この境界の外は信頼していない」「この経路は存在しない」という前提を先に渡せば、
**探す範囲が絞られます。**

### ② severity があなたの文脈で再較正される

`/triage` は、検出結果の深刻度を**脅威モデルに照らして調整します**。
ここで効くのが手順 ① のリスク評価です。ツールの既定値ではなく、
**あなたが Impact × Likelihood で付けた評価**が判断材料になります。

### ③ 「調べなくてよいこと」を伝えられる

これが **Deprioritized セクションの価値**です。
「誤検知と判断した」「自分たちの環境には該当しない」「残留リスクとして受け入れた」は、
**コードをいくら読んでも分からない人間の決定**です。伝えなければ、AI は毎回同じ指摘をします。

### ④ 埋まっていない項目が明示される

Open questions には、**このツールでは埋められなかった項目**が正直に並びます
（攻撃者像が未モデル化であること、未評価の脅威に既定値を使ったこと、など）。
**「書いていないこと」が分かる**ので、AI の出力を鵜呑みにせずに済みます。

## 7. 変換の限界

**この変換はロスありです。** 公式の形式に無い情報は縮退するか、落ちます。

- **エージェント特有の属性**（権限の広さ・侵害時の影響範囲・アイデンティティの強度・
  ツール呼び出しやメモリ読み書きといったデータフローの意味）**には対応する列がありません。**
  緩和策の本文に残る範囲を除いて、出力には現れません
- **攻撃者（`actor`）列は空**です。このツールは攻撃者像をモデル化していません
- **`evidence` 列は常に空**です。確定した証拠（CVE や所見へのリンク）を保持していないためです
- **`sensitivity` は全資産で `medium` 固定**です

**これらはすべて Open questions に明記されます。** 隠していません。
エージェント特有の観点まで含めて議論したいときは、**この Markdown だけを渡すのではなく、
図そのものや脅威カードの本文も一緒に共有してください。**

---

## 8. 結果を図に戻す

AI から返ってきた指摘は、**いまのところ手作業で図に戻します。**

1. 指摘がどの脅威に対応するかを、ファイル末尾の対応表で確認する
2. CyberRiskScape 側で該当する脅威を開く
3. 確認できた指摘は**対策実装状況**に、対象外と分かったものは**対応方針**に記録する
4. 次回の出力に、その判断が反映される

この往復を回すほど、Deprioritized が厚くなり、**次の診断はより静かになります。**

---

## 9. つまずきやすいところ

**Q. 出力した脅威の件数が、画面の件数と合わない。**
誤検知と対策対象外にしたものは脅威表から外れ、Deprioritized に移ります。
消えたのではなく、別のセクションにあります。

**Q. `impact` が画面の severity と違う。**
リスク評価を付けていれば、**評価由来の値**が出ます。ルール由来の severity は一般論なので、
評価済みならそちらが優先されます。CSV には両方（ルール由来と実効値）の列があります。

**Q. すべての脅威の `likelihood` が `possible` になっている。**
リスク評価が 1 件も付いていない状態です。手順 ① に戻ってください。

**Q. 図に描いた影響範囲（BLAST RADIUS）の枠が資産に出てこない。**
影響範囲の枠は注記であって資産でも信頼境界でもないため、意図的に資産一覧へ出していません。

**Q. 出力を手で編集してよいか。**
見出し・列名・列の値は下流ツールとの取り決めです。**説明文の加筆は問題ありませんが、
構造は崩さないでください。**

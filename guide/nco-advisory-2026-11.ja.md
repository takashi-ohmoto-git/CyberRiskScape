## 1. このページで分かること・前提

- 注意喚起の対策事項（運用・管理段階の 1-(1)〜1-(3)、設計・開発段階の 2-(1)〜2-(3)、サプライチェーンの 3-(1)・3-(2)）を、
  **CyberRiskScape のどの画面・コマンドで確かめるか**
- ウェブサイトとモバイルアプリを持つ架空の会員サイトの図（テンプレート）と、その図で出る脅威
- 脆弱性の指摘・SBOM・外部から見える資産を**図に重ねて、どれから直すかを決める**コマンドの流れ（§5）
- 12 項目の**注意喚起チェックリスト**と、CI で止める使い方

**注意喚起の要旨**

個人情報の漏えいにつながる不正アクセスが続いています。注意喚起は、ウェブサイトやモバイルアプリについて、
基本的な対策を徹底するよう求めています。中心の考え方は 2 つです。

1. **AI を使うと、個々には評価が低い脆弱性や設定の甘さを組み合わせて、侵入の足がかりにされうる。**
   評価の高いものだけを直しても足りない。
2. **自分が把握している資産の一覧（台帳）と、外から実際に見えている状態を突き合わせ続ける。**
   把握していない公開サービスや、閉じたつもりの管理画面が残っていないかを見る。

**CyberRiskScape が担う範囲**

CyberRiskScape は**設計（構成図）から脅威を洗い出し、他の製品の結果を図に重ねて文脈をつける**ツールです。
診断や ASM の**実行**、脆弱性・サポート終了の情報の**保有**、ライセンスの**適否の判定**、委託先の**評価**はしません。
「悪用できる」「検知できる」とも言いません。出すのは、図と取り込んだ記録から読み取れる**事実と推奨**です。判断は人が行います（§8）。

**前提**

- 前提となる知識：[はじめに](getting-started.ja.md)、[脅威パネルの読み方](reading-threats.ja.md)、[テンプレートを作る・使う](templates.ja.md)
- このページのコマンドは `dist-cli/main.js` を使います。`npm run build:cli` で作ります（[AI駆動開発のCIに組み込む](ci-integration.ja.md)）。
  Node.js が要ります。Python や外部のネットワークは要りません
- 取り込む SBOM・KEV・ASM の各ファイルは、**別の製品や公開元から自分で用意します**（CyberRiskScape は同梱しません・取得もしません）。
  このページでは、同じ場所に置いた架空の小さなサンプルを使います

## 2. 題材の会員サイトとアプリ — テンプレートを読み込んで構成を確認する

次のような**架空のシステム**を 1 つのレイヤーに描きました。

- 会員は、ブラウザ（会員サイト）とスマートフォンのアプリから使う。入口の前段に、リバースプロキシ（CDN を含む）がある
- 会員サイトはフロントエンドサーバー、アプリは API ゲートウェイ経由で会員 API を呼ぶ。会員 API が会員 DB（個人情報）と、帳票・画像の保管先を使う
- **管理画面**は、前段のリバースプロキシが URL のパスで振り分けた先にある。管理画面自体にグローバル IP は付けていない
- 保守は委託先の担当者が、保守用の VPN 装置から踏み台を通して行う
- CI パイプラインが会員 API に配備する。**本番の会員 DB と CI は、同じクラウドのアカウント（管理境界）に同居している**
- 攻撃者（AI を使って弱い点の組み合わせを探す）は、標的を会員 DB に設定している

| ファイル | 内容 |
|---|---|
| [`templates/nco-advisory-2026-11.ja.json`](templates/nco-advisory-2026-11.ja.json)（[英語版](templates/nco-advisory-2026-11.en.json)） | テンプレート。アプリに読み込む（[読み込み方](templates.ja.md#3-読み込むimport)） |
| [`templates/nco-advisory-2026-11-project.ja.json`](templates/nco-advisory-2026-11-project.ja.json)（[英語版](templates/nco-advisory-2026-11-project.en.json)） | 同じ図をプロジェクト JSON にしたもの。CLI にそのまま渡せる（§5） |
| `templates/nco-sample-*` | §5 で使う架空のサンプル（SBOM 2・KEV 1・Shodan 風の観測 1・ホストとノードの対応表 1） |

**図の中身：** コンポーネント 16・データフロー 17・境界 5（信頼境界 3、管理境界 1、開発の区画 1）。
読み込むと **140 件**の脅威が検出されます（Critical 14・High 73・Medium 53。実測）。

| 場所 | 描いたもの（型） |
|---|---|
| 外部境界（Internet） | 会員（`ユーザー`。スマートフォンを内包）、保守委託先の担当者（`ユーザー`。信頼区分は委託先）、攻撃者（`AIエージェント攻撃者`） |
| 公開セグメント（Public Area） | 前段のリバースプロキシ・CDN（`リバースプロキシ`）、会員サイト（`フロントエンドサーバー`）、API ゲートウェイ、IdP、保守用 VPN 装置 |
| 内部セグメント（Internal） | 管理画面（`管理画面`）、会員 API（`バックエンドAPI`）、踏み台、会員 DB（`データベース`。個人情報を内包）、帳票・画像の保管（`ストレージ`）、CI パイプライン |
| 管理境界（アカウント等） | 会員 DB・帳票・画像の保管・CI パイプラインを囲む。CI の周りは「開発」の区画 |

**意図的に未入力にしたもの。** 管理画面の「リモートアクセス制限」、API ゲートウェイの「レート制限」、
踏み台・VPN 装置・IdP・CI パイプラインの運用状況などは空です。
CyberRiskScape は**未入力を悪い値と同じ扱い**で脅威を出します。画面では「仮定検出」の印が付き、実態を入力すると消えます。

**この図で出る、注意喚起に直結する脅威**（読み込んだ直後の実測）

| 脅威 | 出る場所 | 重大度 |
|---|---|---|
| 前段の振り分けルールを経由した管理面への到達 | C10 管理画面 | High |
| ログイン・パスワード再設定の入口への総当たり・リスト型攻撃 | C6 会員サイト・C7 API ゲートウェイ | Medium |
| IdP のログイン画面への総当たり・リスト型攻撃 | C8 IdP | High |
| ブラウザの JavaScript に埋め込んだ秘密情報による呼び出し元の確認 | DF4（会員のブラウザ → API ゲートウェイ） | Medium |
| 外部協働者（委託先）の機微システムアクセス | DF7（委託先 → VPN 装置） | Medium |
| 本番のデータと開発・CI が同じ管理境界に同居 | C13 会員 DB・C15 帳票・画像の保管 | High |

> **描き方のメモ。** 管理画面を `フロントエンドサーバー` ではなく `管理画面` 型で描いたのは、管理面に固有の脅威を出すためです。
> 管理画面の「グローバル IP」を「無し」と入力しているのは、「外には出していないつもり」の状態を表すためです。
> それでも前段から線が届いていれば、前段経由の到達が出ます。

## 3. 注意喚起の対策事項と CyberRiskScape の対応

表の「出るもの」は、このページの図で実際に出たものです。「しないこと」は、**ツールの範囲外**で、別の手段が要るものです。
**手段が複数あるものは、どれか一つで足ります**（例：ASM は Shodan か ScopeSentry のどちらか。SBOM は CycloneDX か SPDX のどちらか）。

### 3.1 運用・管理段階

| 要求 | CyberRiskScape でどこを見るか・何をするか | 出るもの | しないこと |
|---|---|---|---|
| **1-(1)** 資産（ソフトウェアの構成情報）の把握と脆弱性の解消 | 手元の SBOM を `import-sbom` でノードに結びつける。KEV カタログを `import-kev` で照合し、`import-epss` で EPSS（悪用の見込み）を付け、`fill-patch-status` で運用状況のパッチを補い、`findings-priority` で P1〜P4 と CISA の SSVC の判定を見る。納品された SBOM は `sbom-report` で検収 | 指摘ごとの優先度と根拠（露出・届く標的・KEV・EPSS・連鎖）と SSVC の判定、SBOM の無いノード・ライセンス欄が空の部品 | 脆弱性の検出、脆弱性・サポート終了の情報の保有、ライセンスの適否の判定 |
| **1-(2)** 攻撃面の継続的な把握と最小化（管理画面・デバッグ用・テスト用・DB 管理を出さない） | 外部から見える資産を `import-shodan --into` か `import-scopesentry --into` で保存し、`asm-reconcile` で図の「外部公開」と突き合わせる。管理画面は `管理画面` 型で描く。アラートの IP・ホスト名は `context` で図に引く | 「図に無いのに外から見える」「非公開と入力したのに外から見える」の一覧、前段経由の管理面への到達 | ASM の実行。見えていないものは一覧に載らない（観測の範囲外） |
| **1-(3)** 継続的なテスト・監視（AI の活用を含む） | `export-test-plan --changed-from` で、変更した部分だけの再診断計画を作る。`export-detection-requirements` で、攻撃経路上の「監視すべき振る舞い」と、ログが監視先に届かない区間を見る。AI を使った診断（AI 自律ペンテストの Strix・CyberStrikeAI、AI によるソース監査の security-audit）の結果も図に取り込める（[OSS で組む脆弱性管理](oss-vulnerability-management.ja.md)・[AI によるソース監査](security-audit.ja.md)） | 再診断の対象ノード、監視要件、ログが届かない区間、AI の診断で実証・要確認とされた指摘 | テストの実行、監視の実施。「検知できる」とは言わない |

### 3.2 設計・開発段階

| 要求 | CyberRiskScape でどこを見るか・何をするか | 出るもの | しないこと |
|---|---|---|---|
| **2-(1)** セキュアバイデザイン（脅威モデリング、要件定義、管理画面を公開しない、ゼロトラスト、クラウドアカウントの分離） | 図を描いて脅威を出すこと自体が脅威モデリング。`export-requirements`（左サイドバーからも出せる）で、設計段階で決める要件のたたき台を作る。本番と開発・CI が同じ管理境界にいないかは、管理境界を描いて確かめる | 緩和策の段階（Foundation / Enterprise / Advanced）つきの要件一覧、管理境界の同居の脅威 | 要件の採否の決定（人が決める）、クラウドの実設定の確認 |
| **2-(2)** API のセキュリティ（認証・認可、レート制限、クレデンシャルスタッフィング） | 公開の入口の攻撃面属性に**レート制限**を入力する。API は `バックエンドAPI`・`APIゲートウェイ` で描く。認可の不備（BOLA・BFLA）は脅威カードの確認観点で | 総当たり・リスト型攻撃（API と IdP）、認可不備、ブラウザ・アプリへの秘密情報の埋め込み | 認可の実装の検証（API のテストで確かめる） |
| **2-(3)** 公開前の脆弱性診断（範囲と観点、ASVS） | `export-test-plan` で診断の範囲と観点を決める。観点には OWASP ASVS 5.0 の要件 ID が参照として付く。診断結果は、SARIF（ZAP・Trivy・SAST）を `import-sarif`、Nuclei を `import-nuclei`、ペンテストの台帳を `import-pentest` で取り込み（[OSS で組む脆弱性管理](oss-vulnerability-management.ja.md)）、`analyze --fail-on-findings` で、しきい値以上が残る間は公開を止める | 診断の範囲・観点・ASVS の参照、残っている指摘の件数 | 診断の実行 |

### 3.3 サプライチェーン

| 要求 | CyberRiskScape でどこを見るか・何をするか | 出るもの | しないこと |
|---|---|---|---|
| **3-(1)** 委託先の管理と接続経路（多要素認証、IP 制限、作業時だけ開ける、ログ、作業後のアカウント削除） | 委託先を `ユーザー`（信頼区分＝委託先）で描き、VPN・踏み台への線の認証方式を実態どおりに入れる。`export-contractor-paths`（左サイドバーからも出せる）で、**多要素認証へ切り替える優先順**の一覧を出す。信頼区分が未入力のユーザーも、社員と確認できない利用者として扱って出る | 接続経路の一覧（認証・MFA 相当か・送信元 IP 制限・ログ）、委託先の常設の保守接続の脅威 | 委託先の評価。判別は推定で、各行は「確認する候補」。作業時だけ開けているか・アカウントを消したかは実機で確かめる |
| **3-(2)** OSS・外部ライブラリの管理（SBOM、脆弱性との突き合わせ、ライセンス、検収） | `import-sbom` で部品とライセンス欄を保存。`sbom-report` で、図に結びつかない部品・古い BOM・ライセンス欄が空の部品を見る。深刻な脆弱性の公表時は `context --purl` で、どのノードに影響するかを引く | 部品ごとのノードへの結びつき、指摘の件数、ライセンス欄の空 | ライセンスの適否の判定、導入の合否の判定 |

## 5. 一連のコマンド — 取り込み、優先度づけ、突き合わせ、書き出し

ここからは、作業用のディレクトリに図を置いて、取り込みから順に実行します。
プロジェクト JSON は、1 つ前のコマンドの `-o`（`--out`）の出力を次のコマンドに渡してつなぎます
（元の `member-site.json` は書き換わりません）。

```bash
cp guide/templates/nco-advisory-2026-11-project.ja.json member-site.json
```

アプリで作った図を使う場合は、左サイドバーの**ファイル（保存 / 開く）**で書き出したプロジェクト JSON を使います。

### 5.1 SBOM を取り込む（1-(1)・3-(2)）

`--node` で、その SBOM の部品をどのノードに結びつけるかを指定します（C 番号は画面のノード番号）。
`--scope` は取り込み直しで置き換える範囲です。**CycloneDX か SPDX のどちらかで足ります。**
CycloneDX の `vulnerabilities` は指摘として保存され、VEX で `not_affected` などのものは除かれます。

```bash
node dist-cli/main.js import-sbom member-site.json --sbom guide/templates/nco-sample-sbom.cdx.json \
  --scope web-app --node C6 -o step1.json
```

```text
- scope: web-app（同じ形式・同じ scope の部品を置き換えた）
- 保存 2 件（software 2）
- 指摘 1 件（除外 1 件）（CycloneDX の vulnerabilities。同じ scope の指摘を置き換えた）
  - 除外: VEX の状態が not_affected・false_positive・resolved のもの
部品を取り込みました（保存 2 / 上限で除外 0、指摘 1 / VEX 等で除外 1）        （終了コード 0）
```

会員 API 側の SBOM も、別の scope で取り込みます。

```bash
node dist-cli/main.js import-sbom step1.json --sbom guide/templates/nco-sample-sbom-api.cdx.json \
  --scope api --node C11 -o step2.json
# 部品を取り込みました（保存 1 / 上限で除外 0、指摘 1 / VEX 等で除外 0）        （終了コード 0）
```

### 5.2 KEV を照合し、パッチ状況を補う（1-(1)）

`import-kev` は、**自分で用意した** CISA の KEV カタログ（JSON）と指摘の CVE を照合します。カタログは同梱せず、ネットワークにも出ません。
最新のカタログを CISA の公開ページから取得して使ってください。このページでは架空の小さなカタログ
（[`templates/nco-sample-kev.json`](templates/nco-sample-kev.json)。`CVE-2099-0001` だけが載っている）を使います。
KEV に載っている＝CISA が悪用を確認した事実です。載っていないことは「悪用されていない」を意味しません。

```bash
node dist-cli/main.js import-kev step2.json --kev guide/templates/nco-sample-kev.json -o step3.json
```

```text
- 照合した指摘（CVE を持つもの）: 2 件 / 印を付けた指摘: 1 件 / 印を外した指摘: 0 件
## ノード別（印を付けた指摘）
- C6 会員サイト: 1 件
KEV と照合しました（対象 2 / 印を付けた 1 / 外した 0）        （終了コード 0）
```

`fill-patch-status` は、CVE を持つ指摘があるノードのうち、運用状況の**パッチが未入力のもの**を「未適用」にします。
入力済みは上書きせず、「更新済み」は書きません（指摘が無いことは更新済みの証明にならないため）。

```bash
node dist-cli/main.js fill-patch-status step3.json -o step4.json
```

```text
- 補完したノード: 1 件
- 見送り: 入力済み 1 / 型がパッチ状況を持たない 0 / ノードに結びつかない指摘 0
- L1 会員サイト（FRONT_END_SERVER）: CVE-2099-0001
パッチ状況を補完しました（補完 1 件）        （終了コード 0）
```

**EPSS を付ける（任意）。** `import-epss` は、FIRST が毎日公開する EPSS（30 日以内に悪用が観測される確率の推定）を、指摘の CVE に付けます。
EPSS の一覧も自分で取得して渡します（同梱せず、ネットワークにも出ません）。このページの CVE は架空なので EPSS が無く、手順だけを示します。

```bash
# 一覧は https://www.first.org/epss/ から取得（epss_scores-YYYY-MM-DD.csv.gz）
node dist-cli/main.js import-epss step4.json --epss epss_scores-2026-11-07.csv.gz -o step4.json
```

### 5.3 指摘の優先度を見る — 低い評価の組み合わせ（1-(1)）

`findings-priority` は、保存済みの指摘を攻撃経路に載せ、推奨の優先度（P1〜P4）と根拠を出します。
**元の深刻度は変えません。** 推奨であり、判断は人です。

```bash
node dist-cli/main.js findings-priority step4.json
```

```text
- 指摘 2 件 / 連鎖 3 件
- SSVC の内訳：Track 1 件 / Track* 0 件 / Attend 1 件 / Act 0 件

## P1（先に確認）（2 件）
| 指摘 | 製品 | 元の深刻度 | ノード | 露出 | 届く標的 | KEV | EPSS | SSVC |
| CVE-2099-0002 example-image-lib@1.0.5 | CycloneDX | Medium | C11 会員 API | 入口（仮定） | C16 CI パイプライン（1 ホップ）、C13 会員 DB（1 ホップ）、… | — | — | Track※ |
| CVE-2099-0001 example-web-framework@4.2.1 | CycloneDX | Medium | C6 会員サイト | 入口（仮定） | C8 会員・従業員の IdP（3 ホップ）、…、C13 会員 DB（4 ホップ） | あり（2099-01-01） | — | Attend※ |

## 組み合わさると標的に届く連鎖
- 経路上で指摘が 2 つ以上のノードに並ぶ連鎖 3 件のうち、個々の指摘はすべて Medium 以下 3 件。
- 【個々は低いが連鎖で届く】攻撃者 → C6 会員サイト → C11 会員 API → C13 会員 DB（指摘の深刻度: Medium / Medium）
                                                                              （終了コード 0）
```

注意喚起の中心の考え方がここに出ます。**2 つの指摘はどちらも Medium です。** 単独なら後回しにされる評価ですが、
攻撃者から会員サイト → 会員 API → 会員 DB と続く経路の上に並ぶので、連鎖として示されます。KEV に載る指摘は先に確認する候補です。

- 「入口（仮定）」は、攻撃面属性が未入力のために、悪い値と仮定して露出を判定したという印です
- **EPSS** は `import-epss` で付けた値です。この例では「—」です。EPSS が 0.1 以上で、攻撃者から届くノードにある指摘は、優先度が 1 段上がります（低くても下がりません）
- **SSVC** は、CISA の SSVC の判定（Track・Track\*・Attend・Act）を、P1〜P4 とは別の物差しとして並べたものです。
  KEV に載る CVE-2099-0001 は Attend（標準より早く対応する）、載らない CVE-2099-0002 は Track（標準の更新期間で対応する）になりました。
  `※` は、未入力や図から決まらない値を悪い側に仮定した印です（この例は CVSS ベクターが無いので、技術的な影響を深刻度から仮置きしています）。
  決め方は [OSS で組む脆弱性管理](oss-vulnerability-management.ja.md) §2 を見てください
- 出力には「経路の列挙が上限に達したため、連鎖に漏れがありうる」の注記が出ることがあります。この図でも出ました。連鎖は「少なくともこれだけ」と読みます

### 5.4 外から見える資産を重ね、図と突き合わせる（1-(2)）

ASM の結果を資産として保存します。**Shodan か ScopeSentry のどちらかで足ります。**
（`import-scopesentry --into` も同じ形です。[ScopeSentry を取り込む](scopesentry.ja.md)）
`--map` は、ホスト名・IP と図のノードの対応表です（対応させないものは「未対応」として残ります）。

```bash
node dist-cli/main.js import-shodan guide/templates/nco-sample-shodan.json --into step4.json \
  --scope shodan-2026-11 --map guide/templates/nco-sample-asm-map.json --out step5.json
```

```text
Shodan のサービスを資産として保存しました（サービス 3 / CVE の識別子 0 / 未対応のホスト 1）        （終了コード 0）
```

`asm-reconcile` は、ASM が観測した資産と、図の「外部公開」（Global IP）の入力の**食い違いを並べる**読み取り専用の報告です。
どちらが正しいかは判定しません。終了コードは常に 0 です。

```bash
node dist-cli/main.js asm-reconcile step5.json
```

```text

## 図に無いのに外から見える（1 件）
| 203.0.113.51 | 203.0.113.51 | 22 | ssh | Shodan | 2026-11-03T03:05:00.000Z |

## 非公開と入力したのに外から見える（1 件）
| 203.0.113.50 | 203.0.113.50 | 8443 | https | Shodan | 2026-11-03T03:00:00.000Z | C10 管理画面 |
```

- **図に無いのに外から見える**：台帳（図）に無い公開サービス。SSH が 1 件見えています。図に描くか、閉じる対象です
- **非公開と入力したのに外から見える**：管理画面（C10）です。図では「グローバル IP 無し」と入力していますが、
  前段のリバースプロキシ経由で外から届いています。注意喚起の「閉じたつもりの管理画面」の例です
- 「公開と入力したが観測に無い」は、観測の範囲外か、図が古い可能性があります

アラートが出たホスト・IP・部品は、`context` で図に引きます（読み取り専用）。MCP の `lookup_context` でも同じことができます
（[MCP で使う](mcp-integration.ja.md)）。


`sbom-report` は、保存済みの SBOM の**検収の補助**です。図との結びつき・新しさ・指摘の件数・ライセンス欄の空を並べます。
合否も、ライセンスの適否も判定しません。終了コードは常に 0 です。

```bash
node dist-cli/main.js sbom-report step5.json
```

```text

## 取り込み単位ごとの状況
| example-sbom-generator | web-app | 2 | C6 会員サイト | 2026-10-15T00:00:00.000Z | — |
| example-sbom-generator | api    | 1 | C11 会員 API  | 2026-10-15T00:00:00.000Z | — |

## 脆弱性（CycloneDX の vulnerabilities 由来の指摘）
| C6 会員サイト | Critical 0 | High 0 | Medium 1 | Low 0 | KEV 1 |
```

- ライセンス欄が空の部品（`example-logger`）は、納品元に確認します。**ライセンスが使ってよいものかは、人が判断します**

### 5.6 要件・委託先の経路・検知要件・再診断計画を書き出す（1-(3)・2-(1)・3-(1)）

書き出しは、いずれも図から作る**たたき台**です。採否・優先度は人が決めます。

```bash
node dist-cli/main.js export-requirements step5.json --out requirements.md
# セキュリティ要件一覧を出力しました（L1・要件 129 件・委託先への要件 6 件）

node dist-cli/main.js export-contractor-paths step5.json --out contractor-paths.md
# 委託先の接続経路を出力しました（L1・1 件）

node dist-cli/main.js export-detection-requirements step5.json --out detection.md
# 検知要件を出力しました（L1・対象ノード 7 件・監視要件 37 件・経路 7 本）

node dist-cli/main.js export-test-plan step5.json --out test-plan.md
# テスト計画書を出力しました（L1・入口 6 件・攻撃シナリオ 1 件・重点テスト項目 140 件・対象外 0 件）
```

（いずれも終了コード 0。`--format` で `csv`・`json` なども選べます。オプションは `--help` を見てください。）

- **要件一覧（2-(1)）**：要件は脅威ごとの緩和策を Foundation / Enterprise / Advanced に分けたものです。
  設計段階で必要な段階を選び、要件定義書や委託先への仕様に取り込みます。左サイドバーの Report からも出せます
- **委託先の接続経路（3-(1)）**：この図では 1 行出ます（委託先の担当者 → 保守用 VPN 装置 → 踏み台）。
  認証が ID/パスワード（MFA 相当でない）で、踏み台の先の会員 DB・個人情報に届く、と出ます。
  会員のブラウザやアプリから API ゲートウェイへの線は、通常の利用として数えません。
  委託先の判別は図の属性・線・型からの推定なので、各行を「確認する候補」として扱います。
  順位は MFA に切り替える優先順です。MFA を入れられない経路は、送信元 IP 制限・作業時だけの開放・操作ログの取得で代えます
- **検知要件（1-(3)）**：攻撃者から標的に至る経路上のノードごとに、監視すべき振る舞いと必要なログを並べます。
  この図は、どの経路も「ログが監視先に届くとは読み取れない」と出ます（ログの送信先を入力していないため）。
  実際に検知できるかは別に確かめます
- **テスト計画（2-(3)）**：脅威ごとの確認観点に、OWASP ASVS 5.0 の要件 ID が参照として付きます（例：`V8.4.2`・`V13.1.2`）。
  診断の範囲と観点を診断事業者と合意する出発点にします。自分が管理する、または許可を得たシステムだけをテストしてください

**変更した部分だけの再診断（1-(3)）。** 図を変更したあとは、前回のモデルとの差分で、再診断の対象を絞れます。
ここでは、CI パイプラインを追加する前の図（`before-ci.json`）と比べた例です。

```bash
node dist-cli/main.js export-test-plan step5.json --changed-from before-ci.json --out retest.md
# テスト計画書を出力しました（L1・入口 0 件・攻撃シナリオ 0 件・重点テスト項目 4 件・対象外 0 件）
```

```text
**再診断の対象ノード**
- C16 CI パイプライン
```

全体で 140 件だった重点テスト項目が、追加したノードに関する 4 件になりました。
前回のモデルは、保存しておいた前のプロジェクト JSON（`git` の前の版など）を渡します。

### 5.7 図を直すと、件数が変わる（2-(2)）

公開の入口（会員サイト・API ゲートウェイ）に、実際にアカウント単位・送信元単位の試行制限を入れたうえで、
攻撃面属性の**レート制限**を「有り」に入力して `diff` を取ると、総当たり・リスト型攻撃の脅威（会員サイト・API ゲートウェイの 2 件）と、
API を使った個人情報の大量取得の脅威（API ゲートウェイ。High）の 3 件が消えます。

```bash
node dist-cli/main.js diff step5.json rate-limited.json
```

```text
- 追加: 0 件
- 解消: 3 件
```

入力を変えるだけでなく、**実態を変えてから入力してください**（入力は観測ではなく宣言です）。分散した試行は、
回数制限だけでは止まりません。脅威カードの対策（失敗率の検知・MFA・パスキー等）も確認します。

### 5.8 CI で止める（1-(3)・2-(3)）

診断の結果（SARIF や SBOM の脆弱性）を取り込んだプロジェクト JSON に対して、**保存済みの指摘**がしきい値以上なら終了コード 1 で止めます。
試行のみの指摘と、受容済みの指摘は数えません。

```bash
node dist-cli/main.js analyze step5.json --fail-on-findings Medium --format md > /dev/null
# --fail-on-findings Medium: 保存済みの指摘が 2 件しきい値以上です（試行のみ・受容済みを除く）。
#   - [Medium] CycloneDX: CVE-2099-0001 example-web-framework@4.2.1 @ 会員サイト
#   - [Medium] CycloneDX: CVE-2099-0002 example-image-lib@1.0.5 @ 会員 API
# （終了コード 1）

node dist-cli/main.js analyze step5.json --fail-on-findings High --format md > /dev/null
# （終了コード 0。High 以上の保存済みの指摘は無い）
```

`--fail-on` は図から出る**脅威**（`diff` では新規の脅威）を数えます。`--fail-on-findings` は取り込んだ**指摘**を数えます。両方付けられます。
CI の組み込み方は [AI駆動開発のCIに組み込む](ci-integration.ja.md) を見てください。
最初は止めずに一覧だけを出し、対応が進んでから止める使い方を勧めます。

## 6. 図を更新し続ける運用

1. **SBOM・KEV・ASM は取り込み直す。** 同じ `--scope` で取り込み直すと置き換わります。KEV は取り込み直すと最新になります（載らなくなった指摘は印が外れます）
2. **観測と図を月次などで突き合わせる。** `asm-reconcile --previous 前回.json` で、新しく見えた・見えなくなった観測を比べます
3. **変更のたびに再診断の範囲を絞る。** `export-test-plan --changed-from`
4. **チェックリストの「点検が古いノード」を空にする。** 運用状況の最終点検日を更新する運用は、[IPA の注意喚起のガイド](ipa-alert-2026-10.ja.md)の §7 と同じです
5. **次の注意喚起は YAML を足すだけ。** チェックリストは `data/checklists/` の YAML で、画面と CLI の両方に出ます

## 7. 図に描けないこと・実機で確かめること

| 注意喚起の対策 | 図からは分からないこと | 確かめる手段 |
|---|---|---|
| 脆弱性の解消 | 実際のパッチの適用状況、サポート終了 | 実機のスキャン、各製品の情報。運用状況の入力は宣言 |
| 公開サービスの最小化 | 観測の範囲外のサービス | ASM の継続実行。取り込んだ範囲だけが突き合わせの対象 |
| 認可の実装 | BOLA・BFLA が本当に無いか | API のテスト（`export-test-plan` の観点を使う） |
| 試行制限・分散した試行の検知 | 制限が効いているか | 認証の入口への試行（自分が許可を得た環境で） |
| 委託先の管理 | 作業時だけ開けているか、作業後にアカウントを消したか | 委託先との契約・運用、アカウント棚卸し |
| OSS の管理 | ライセンスが使ってよいか、BOM の完全性 | 法務・調達の判断、SBOM を作る側の確認 |

## 8. 限界

- **CyberRiskScape は診断・ASM・EDR ではありません。** 取り込んだ結果に文脈をつけるだけです。見えていないものは出ません
- **脆弱性・サポート終了のデータベースは持ちません。** 指摘は、取り込んだ SBOM や診断結果の中身です。KEV は自分で用意したファイルとの照合です
- **ライセンスの適否・委託先の評価・導入の合否は判定しません。** 事実の一覧です
- **「悪用できる」「検知できる」とは言いません。** 優先度は推奨と根拠で、判断は人が行います。KEV に載る＝CISA が悪用を確認した事実で、載らない＝悪用されていない、ではありません。EPSS は確率の推定で、SSVC の判定も図と取り込んだ記録からの推奨です
- **LLM は呼びません。** 書き出しはルールとデータから機械的に作ります
- **経路の列挙は上限に達すると漏れます。** 連鎖は「少なくともこれだけ」と読みます
- チェックリストの項目と脅威ルール・型の対応は、**CyberRiskScape 側の解釈**です。国家サイバー統括室が定めたものではありません

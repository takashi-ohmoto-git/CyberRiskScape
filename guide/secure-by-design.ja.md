# Secure by Design 入門

[English](secure-by-design.md) | **日本語**

このページは CyberRiskScape の操作説明ではありません。
**なぜ設計の段階で脅威を考える必要があるのか**、その背景にある「Secure by Design」という
考え方を説明します。操作から始めたい方は [はじめに](getting-started.ja.md) へどうぞ。

内容は CISA（米国サイバーセキュリティ・インフラストラクチャセキュリティ庁）ほか
18 機関による共同ガイダンス *Shifting the Balance of Cybersecurity Risk* に基づきます。
正確な書誌情報は[末尾の出典](#出典)を参照してください。

---

## 1. Secure by Design とは

**Secure by Design** とは、技術製品が**攻撃者に侵入されないように「設計の時点から」作られている**
状態を指します。ガイダンスはこれを、製品開発の各段階に資源を投じる取り組みであり、
**後から「後付け（bolted on）」することはできない**ものだと述べています。

対になる概念が **Secure by Default** です。こちらは製品が**箱から出した時点で**、
追加費用なしに、よくある攻撃手法に耐えられる状態を指します。
ガイダンスはこれを、新車に標準装備されるシートベルトに例えています。

> セキュリティは贅沢なオプションではなく、交渉や追加の支払いなしに顧客が受け取るべき権利である。
> — ガイダンス本文より（要約）

この 2 つを実現するために、ガイダンスは 3 つの原則を挙げています。

| # | 原則 | 意味 |
|---|---|---|
| 1 | **顧客のセキュリティ成果に責任を持つ** | セキュリティの負担を顧客だけに負わせない。製品側で引き受ける |
| 2 | **徹底した透明性と説明責任を受け入れる** | 脆弱性情報を正確・完全に公開し、安全であることを競争力にする |
| 3 | **経営層が主導する** | セキュリティを技術的な一機能ではなく事業上の優先事項として扱う |

重要なのは、これらが**開発が始まる前**に効く原則だという点です。
Secure by Design な製品は、開発着手前の段階で「顧客の安全」を事業目標として構想されます。

## 2. なぜ今 Secure by Design が求められるのか

### 2.1 「Vulnerable by Design」という現状

ガイダンスは冒頭の章を **"Vulnerable by Design"（設計からして脆弱）** と題しています。

これまでのソフトウェア業界は、**製品を出荷した後に見つかった脆弱性を直す**ことに依存してきました。
その結果、顧客は自らの費用と時間で、監視・定期更新・被害の後始末を延々と続けることになります。
ガイダンスはこれを「修正を作り続け、当て続ける悪循環」と呼び、
**Secure by Design を取り入れることでしか断ち切れない**としています。

### 2.2 脆弱性の多くは少数の根本原因から生まれる

Secure by Design な製品であっても脆弱性はなくなりません。
しかしガイダンスは、**大量の脆弱性が比較的少数の根本原因に由来する**ことを指摘しています。

裏を返せば、個別の不具合を 1 件ずつ潰すのではなく、
**原因のクラスごと設計で消す**アプローチに意味がある、ということです。
メモリ安全な言語の採用、自動エスケープするテンプレート、パラメータ化クエリ、
多層防御（defense-in-depth）といった具体策は、いずれもこの発想に立っています。

### 2.3 規制と市場が動いている

- **EU サイバーレジリエンス法（CRA）** — 製品ライフサイクル全体でセキュリティを実装し、
  脆弱な製品を市場に出さないことを製造者に求めています。
- **Secure by Demand** — ガイダンスは顧客側にも役割を求めます。調達やベンダー評価の過程で
  厳しく問うことで、市場全体をより安全な製品へ動かす、という考え方です。
- **国際的な合意** — 本ガイダンスには日本の NISC・JPCERT/CC を含む 18 機関が名を連ねています。
  これは特定の国のローカルな要請ではありません。

### 2.4 AI も例外ではない

ガイダンスは、**AI ソフトウェアやモデルの製造者にも本書が適用される**と明記しています。
AI 固有の事情に合わせて個々の実践を調整する必要はあるものの、
**3 つの原則はすべての AI システムに当てはまる**という立場です。

CyberRiskScape が LLM・AI エージェント・MCP サーバ・エージェントメモリを
第一級のコンポーネントとして扱うのは、この前提に沿っています。
新しい構成要素が増えても、設計段階で脅威を考えるという原則は変わりません。

## 3. 脅威モデリングの役割

ガイダンスの中で、脅威モデリングは**セキュリティ施策のひとつ**としてではなく、
**Secure by Design を成立させる土台**として繰り返し登場します。整理すると 4 つの役割があります。

### 3.1 設計段階で「起こり得ること」を洗い出す

ガイダンスは、**製品開発の段階で、その製品に合わせた（tailored）脅威モデル**を用い、
システムに対する潜在的な脅威と、各システムの展開方法まで考慮することを推奨しています。
出荷後に見つけて直すのではなく、設計図の段階で防御を組み込むための入口がここです。

### 3.2 「何を、誰から守るのか」を文書にする

ガイダンスは推奨事項として **「高レベルの脅威モデルを公開すること」** を挙げ、
Secure by Design な製品は **「何を守ろうとしているのか、誰から守るのかを記述した、
書かれた脅威モデル」から始まる**と述べています。

さらに、有効な脅威モデルは**実際に侵入が起きている手口に基づいている**べきであり、
企業環境・開発環境、そして顧客環境での想定される使われ方までを対象にすべきだとしています。

ここで求められているのは、頭の中の理解ではなく**書かれた成果物**である、という点が重要です。

### 3.3 優先順位を決める

脅威モデルは、**資源配分と開発において、最も重要で影響の大きい機能に優先順位を付ける**ために
使われます。脅威モデルは製品固有のユースケースを踏まえるため、開発チームが
どこを固めるべきかを判断できる、というのがガイダンスの論旨です。

同じ考え方は導入計画にも適用され、Secure by Design の実践をどの順で取り入れるかは
**その製品に合わせた脅威モデリング・重要度・複雑さ・事業影響に基づいて優先順位付けすべき**
だとしています。

### 3.4 「既定値」を決める根拠になる

Secure by Default では、どの機能を既定で有効にするか、どの設定が安全のために必要かを
決めなければなりません。ガイダンスは、**明示的な脅威モデリングがその判断を助ける戦術**である
と述べています。

既定で有効な機能はそのまま顧客の攻撃面になります。
「便利だから既定で有効」ではなく、「脅威を見たうえで、既定をこう決めた」と言えるかどうかです。

## 4. CyberRiskScape はどこを担うか

上の 4 つの役割に対して、このツールが引き受けるのは次の部分です。

| 脅威モデリングの役割 | CyberRiskScape での対応 |
|---|---|
| 何を・誰から守るか | 構成図として明示する。攻撃者コンポーネントと Objective（標的）で「誰から」を図に書ける |
| 潜在的な脅威の洗い出し | 構成に反応して脅威を自動列挙する。手作業の洗い出しの抜けを補う |
| 実際の手口に基づく | 脅威ライブラリは OWASP・MITRE ATLAS・NIST・Anthropic 等の公開ソースを出典として作られている |
| 優先順位付け | severity とリスク評価、対応方針（低減／受容／移転／回避）を脅威ごとに記録する |
| 段階的な導入計画 | 緩和策を FOUNDATION / ENTERPRISE / ADVANCED の 3 段階で提示する |
| 書かれた成果物にする | 脅威一覧を CSV / JSON / Markdown で書き出せる |

一方で、**このツールが Secure by Design への適合を証明するものではない**ことは
はっきりさせておきます。ガイダンスが求めているのは組織としての取り組みであり、
図とリストはその出発点にすぎません。

- 検出された脅威は脅威ライブラリが覆う範囲のものです。網羅性は保証されません。
- リスクの大きさ、受容するかどうかの判断は利用者が行います。
- SSDF・CRA その他の枠組みへの適合を主張する根拠にはなりません。

それでも、**「書かれた脅威モデル」を作る作業の大部分**——構成を描き、脅威を列挙し、
根拠を残し、成果物として出力する——は、このツールで進められます。

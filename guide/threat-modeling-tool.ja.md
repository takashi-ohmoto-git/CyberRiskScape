# Microsoft Threat Modeling Tool の脅威モデルを移行する — .tm7 を取り込み、移行レポートで差を見る

[English](threat-modeling-tool.md) | **日本語**

> Microsoft Threat Modeling Tool は Microsoft Corporation の製品です。このページは「Microsoft Threat Modeling Tool で作った
> 脅威モデル（.tm7）を CyberRiskScape に取り込む方法」を説明するもので、Microsoft が提供・認定・推奨するものではありません。記述的な使用です。
> .tm7 の公開仕様は無いため、取り込みは執筆時点（2026 年 11 月）の Microsoft Threat Modeling Tool 7.3（ファイル形式 4.3）で作成したファイルから
> 形を確かめて作っています。検証は架空のサンプルと、作者が作成したテスト用のモデルで行いました。

---

## 1. このページで分かること・前提

- Microsoft Threat Modeling Tool（以下 TMT）の .tm7 を、CyberRiskScape のプロジェクトとして取り込む方法（画面・CLI の `import-tm7`）
- 取り込みで**何がどこに入るか**。移行が目的なので、**どの情報も捨てません**（担当者の名前・脅威の判断の理由・メモも残ります）
- TMT で付けた脅威と、CyberRiskScape が同じ図から検出した脅威を突き合わせる**移行レポート**の読み方
- 取り込んだ後に人が確かめること、そして**限界**

**前提**

- TMT で保存した .tm7 がある（TMT 7.3 で作成したファイルで確認しています）。
- 画面だけで使えます。CLI を使う場合は Node.js が動き、CLI をビルドしておきます（`npm ci && npm run build:cli`）。
- .tm7 は手元のブラウザ（または CLI）で読むだけです。どこにも送信しません。

**このページの前提となる知識**：[はじめに](getting-started.ja.md)の操作と、[脅威パネルの読み方](reading-threats.ja.md)。

## 2. 手順

### 2.1 画面から取り込む

1. **Template** を開き、**Import（読み込み）** タブを選びます。
2. **「.tm7（Microsoft Threat Modeling Tool）を選択」** を押し、.tm7 を選びます。
3. 取り込んだ件数（ノード・線・境界・注釈・脅威・対策の状況）と、**要確認の件数**が表示されます。
4. 適用すると、**今のプロジェクトは取り込んだ内容で置き換わります**（確認があります）。必要なら先にプロジェクトを保存してください。

### 2.2 CLI で取り込む

```bash
node dist-cli/main.js import-tm7 model.tm7 --out project.json --report migration-report.md
```

- `--out`：取り込んだプロジェクト JSON。画面の **Template** → **Import** で開けます。`analyze` など他のコマンドの入力にも使えます。
- `--report`：移行レポート（Markdown）を同時に書き出します（§4）。
- `--locale en`：ノードの説明・注釈・レポートを英語で書きます（既定は日本語）。
- 標準エラーに件数と、要確認の要素（名前と理由）を表示します。

移行レポートだけを後から作り直す場合（属性を入力した後など）：

```bash
node dist-cli/main.js migration-report project.json --out migration-report.md   # --format json で JSON
```

画面では、左のサイドバーのプロジェクトのメニューに **「TMT からの移行レポート（Markdown）」** が出ます（TMT から取り込んだ脅威があるときだけ）。

## 3. 何がどこに入るか

### 3.1 図

| TMT | CyberRiskScape | 補足 |
|---|---|---|
| 要素（プロセス・外部の対象・データストア） | ノード | 型は対応表で決めます（§3.2）。位置は TMT の図形の中心に合わせます |
| 要素の名前 | ノードの名前 | |
| 要素の型・選び直した属性・Out Of Scope とその理由 | ノードの **説明** に `[TMT]` 付きで記録 | 既定の選択のままの属性は書きません（型から元の値が分かるため） |
| データフロー | 線（向きは TMT と同じ） | 名前・プロトコル（HTTP / HTTPS など）・説明も入ります |
| データフローの「Provides Confidentiality」 | 線の暗号（Yes → TLS、No → 平文） | 分からなければ平文（悪い値）として扱います |
| データフローの「Source Authenticated」 | 線の認証（Yes → パスワード、それ以外 → なし） | 認証の方式は TMT に無いため控えめに入れます。実態に合わせて引き上げてください |
| 枠の形の信頼境界（CorpNet など） | 境界（CorpNet は社内のマクロセグメント） | 両端が同じ枠の中にある線は経路を VPC、それ以外は Internet にします |
| **線の形の信頼境界**（Internet Boundary など） | **注釈**（座標つき）＋要確認 | CyberRiskScape の境界は「領域」なので、そのままは描けません（§5） |
| どこにもつながっていないデータフロー | 注釈（座標つき）＋要確認 | |
| メモ（Notes） | 注釈（追加した人・日時つき） | |
| 図（タブ）が複数 | 1 枚目から順に L1・L2・L3・L0 のレイヤー | 5 枚目以降は取り込まず、名前を表示します |

### 3.2 型の対応

意味がはっきり一致する型だけを専用の型にし、それ以外は DFD の基本の型（プロセス・データストア・外部主体）に置きます。
型を寄せると当たる脅威ルールが変わるため、迷うものは寄せていません。

| TMT の型 | CyberRiskScape の型 |
|---|---|
| Web Server・Web Application | フロントエンドサーバー |
| Web Service | バックエンド API |
| Human User | ユーザー |
| Browser | パソコン（利用者の端末） |
| Authorization Provider | IdP |
| External Web Application・External Web Service | SaaS |
| SQL Database・Non Relational Database | データベース |
| Cloud Storage | ストレージ |
| HTTP・HTTPS・IPsec・SMB など | 線のプロトコル |
| スレッド・レジストリ・名前付きパイプ・仮想マシンなど | プロセス・データストアなど DFD の基本の型 |

**Azure のテンプレートや独自のテンプレートの型**は、対応表に無くても、その親の型（プロセス・外部の対象・データストア）として取り込みます。
元の型はノードの説明に残し、`[TMT] 要確認` を付けます。

### 3.3 モデル情報と脅威

| TMT | CyberRiskScape |
|---|---|
| Threat Model Name・High Level System Description | プロジェクトの名前・目的 |
| Owner・Reviewer・Contributors・Assumptions・External Dependencies | プロジェクトの責任者・レビュー担当・関係者・前提条件・外部依存（プロジェクトの編集で変えられ、報告書にも出ます） |
| 脅威（題名・説明・STRIDE の分類・Priority） | **手動脅威**として、そのデータフローの線に紐づけます。Priority は重大度に入ります |
| 状態 Mitigated / Not Applicable / Needs Investigation | 対策の実装状況 実装済み / 対象外 / 要対応 |
| Justification・変更した人・変更日時 | 実装状況のメモ・変更者・日時 |
| 脅威の ID・種類・元の状態などの全項目 | 手動脅威の元の記録として、読み替えずにそのまま保存 |

TMT で未着手のままの脅威（Not Started）は、実装状況を付けずに取り込みます。

> 画面で実装状況を変えると、変更者の表示は消えます。CyberRiskScape は操作している人を知らないため、残すと別の人の変更が
> 元の人の名前で表示されてしまうからです。TMT の元の変更者は、手動脅威の元の記録に残っています。

## 4. 移行レポートの読み方

TMT から取り込んだ脅威と、CyberRiskScape が同じ図から検出した脅威を、**要素（線とその両端）× STRIDE の分類**で突き合わせます。
TMT の脅威は STRIDE の汎用の問いで、CyberRiskScape のルールとは 1 対 1 に対応しないため、名前では照合しません。
「重なり」は、同じ問いに具体的な脅威が当たっていることを示すだけで、同じ脅威であることは意味しません。

| 章 | 内容 | 使い方 |
|---|---|---|
| 1. 概要 | TMT の脅威の件数（状態別）、検出脅威の件数（重大度別）、重なった件数、未入力の仮定で出た件数 | 移行の規模をつかむ |
| 2. 判断の見直し候補 | TMT で Mitigated・Not Applicable にしたのに、同じ要素・分類で、抑制されていない検出脅威があるもの（変更者つき） | **まずここを見る。** TMT での判断の前提が、具体的な脅威にも当てはまるかを確かめる |
| 3. TMT の脅威ごとの対応 | 全件と、当たった検出脅威 | 引き継ぎ漏れがないかを見る |
| 4. CyberRiskScape だけが検出した脅威 | どの TMT の脅威とも重ならない検出脅威（重大度の高い順、仮定の印つき） | TMT の既定のテンプレートに無い観点（型ごとの具体的な脅威・AI・エージェントなど） |
| 5. 次の作業 | 取り込み後にすること | §5 と同じ |

要素には画面と同じ表示 ID（C1・DF1 など）が付くので、同じ名前の要素も区別できます。

## 5. 取り込んだ後に確かめること

1. **`[TMT] 要確認` を見る。** 対象は、対応表に無い型・線の形の信頼境界・つながっていない線です。
   - 線の形の信頼境界は、注釈の座標を手がかりに、CyberRiskScape の境界（領域）で描き直してください。インターネット側の要素は、
     どの境界にも入れなければ Internet として扱われます。
   - つながっていない線は、両端の要素につなぎ直してください。
2. **「未入力のため仮定」の脅威を見る。** TMT で「Not Selected」のままの属性は、CyberRiskScape では悪い値として扱われます
   （未入力の属性は危ない側の値と同じ扱い）。認証の方式・暗号・攻撃面・運用状況など、実態を入力すると仮定の脅威は消えます。
3. **移行レポートの 2 章の判断を、CyberRiskScape の脅威の対応方針・実装状況に記録し直す。**

## 6. 限界

- .tm7 の公開仕様は無いため、確認した形（TMT 7.3・ファイル形式 4.3）に合わせて読んでいます。版によっては読めないか、
  一部が欠けることがあります。取り込み後に、要素・線・脅威の件数を TMT の画面と照らしてください。
- TMT のテンプレートの**脅威の生成条件は使いません**。脅威は CyberRiskScape の脅威エンジンが改めて出します。
- 認証の方式（MFA・証明書など）、データの種類など、TMT に無い情報は入りません。取り込み後に入力してください。
- 書き出し（CyberRiskScape → .tm7）はありません。
- 画面で取り込むと、今のプロジェクトは置き換わります。

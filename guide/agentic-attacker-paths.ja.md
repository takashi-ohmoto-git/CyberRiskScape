# エージェント型ペネトレーションツールを攻撃者が悪用する前提で、攻撃経路のどこを切るかを図で決める

[English](agentic-attacker-paths.md) | **日本語**

> 自律的に動くエージェント型のペネトレーションテスト用ツールを、攻撃者が悪用する想定です。
> このページは、そうしたツールが**現時点で持っている能力**を防御側の言葉に直し、
> CyberRiskScape の攻撃経路分析の上で「どこを切れば攻撃者の探索が止まるか」を決める手順をまとめます。
>
> 特定の製品の名前・内部の仕組み・攻撃の手順は載せていません。ここで言う「能力」は、この種のツールに共通する一般的な性質です。
> 件数は図によって変わります。あなたの図で実測してください。

---

## 1. このページで分かること・前提

- 自律型の攻撃エージェントが持つ能力を、**4 つの性質**に整理して防御側の前提にする
- その能力を [攻撃経路分析](attack-paths.ja.md) の図の上で追い、**起点・足がかり・連鎖の枝**を特定する
- どのチョークポイントを押さえると、攻撃者の探索木の枝が最も多く刈れるか
- 「面倒にするだけ」の対策が、自律型相手になぜ時間稼ぎになるか（[既存ガイドの §4「面倒にする／不可能にする」](ai-agent-attack-2026-10.ja.md) に接続）

このページは [攻撃経路分析](attack-paths.ja.md) の続きです。攻撃者コンポーネントの置き方・チョークポイントの読み方は先にそちらを読んでください。
**自社でこの種のツールを正規に運用する**側の守りは、別ページ [エージェント型ペネトレーションツールを自社で運用する場合の守り](agentic-pentest-operation.ja.md) にまとめています。

---

## 2. 現時点のこの種ツールが持つ 4 つの性質

攻撃者がこの種のツールを使うとき、防御側は次の 4 つを「あるもの」として設計します。

| 性質 | 防御側にとっての意味 |
|---|---|
| **自律・並列・粘り強い** | 人が手順を踏むのではなく、ツールが目標を分解し、複数の作業を並行させ、休まず試す。→ 検知できても**人の対応が間に合うか**で対策を評価する |
| **発見を足がかりに探索木を広げる** | 一つの発見（弱点・資格情報・内部情報）から、次に何を試すかを動的に選び、横展開の枝を伸ばす。→ 対策は「一つ塞いだら次にどこへ向かうか」まで一手先を読む |
| **外から見える資産を起点にする** | 公開された資産の台帳（外部攻撃面）を取り込み、そこから探索を始められる。→ 最初の入口は「外から見えている資産」。露出の棚卸しが先 |
| **応答を休まず読み込む** | やり取りした通信の応答を全文で検索し、混じっている秘密情報・内部アドレス・トークンを次の足がかりにする。→「応答に何を出すか」の設計が効く |

この 4 つは、攻撃を**速く・多く**するだけでなく、**探索木の広げ方**を変えます。防御側の攻撃経路図は、この探索木の鏡像です。

AI システムへの攻撃手法をまとめた [MITRE ATLAS](https://atlas.mitre.org/)（2026.09 版）は、自律型の攻撃エージェントの振る舞いを technique として定義しています。4 つの性質との対応は次のとおりです。

| 性質 | 対応する ATLAS の technique |
|---|---|
| 自律・並列・粘り強い | [AML.T0124 Autonomous Attack Orchestration](https://atlas.mitre.org/techniques/AML.T0124)（複数のエージェントによる攻撃の自律的な統制） |
| 発見を足がかりに探索木を広げる | [AML.T0117 Autonomous Attack-Path Adaptation](https://atlas.mitre.org/techniques/AML.T0117)（攻撃経路の自律的な組み立てと修正） |
| 外から見える資産を起点にする | [AML.T0116 Autonomous Reconnaissance](https://atlas.mitre.org/techniques/AML.T0116)（自律的な偵察） |
| 応答を休まず読み込む | 専用の technique はありません。近いのは [AML.T0126 Automated Collection](https://atlas.mitre.org/techniques/AML.T0126)（自動化された収集） |

上の 3 つ（T0124・T0117・T0116）は、攻撃者カード `zt-agentic-attacker-ai-accelerated-001` の出典に入っています（§3・§6）。

## 3. 能力を攻撃経路の図の上で追う

[攻撃経路分析](attack-paths.ja.md) で攻撃者コンポーネントから標的までの経路を出したら、上の 4 性質を次のように重ねて読みます。

- **起点（外から見える資産）** — 攻撃者コンポーネントがつながる侵入点が、外部に露出した資産かどうか。公開ポータル・API・管理面・VPN などが該当します。ここが探索木の根です。
- **足がかり（応答に混じる情報）** — 経路の途中のホップで、エラー応答・大量取得・埋め込まれた秘密情報のルールが出ているか。これらは「応答が次の一手を生む」ノードです。
  - `api-error-response-disclosure-001`（詳細なエラーが内部構造を漏らす）
  - `api-bulk-data-harvesting-001`（大量取得で情報が束で漏れる）
  - `api-mobile-embedded-secret-001`・`api-dev-workspace-secret-exposure-001`（応答・成果物に秘密情報）
- **連鎖の枝（発見からの横展開）** — 取得した資格情報・秘密情報が、別のコンポーネントへの次のホップを開くか。秘密情報が一箇所に集約されていれば、そこが踏まれると枝が一気に広がります。
  - `api-secrets-vault-concentration-001`・`nhi-long-lived-secret-001`・`zt-credential-sprawl-static-secret-001`

攻撃者を 「**AIエージェント攻撃者**」のコンポーネントで置くと、攻撃者カード `zt-agentic-attacker-ai-accelerated-001` が出て、この「自律・加速する攻撃者」を前提にした対策の読み替えが示されます。

## 4. どこを切ると探索が止まるか

攻撃経路分析のチョークポイント（1 つの対策が最も多くの経路に効く要素）を、探索木の枝刈りとして使います。優先順位は次の順です。

1. **根を消す（起点をなくす）** — 外部に露出した入口を、確認済みの端末と利用者だけを中継するゼロトラストアクセスの背後に置く。届く経路がそもそも無ければ、探索木は生えません。業務 API の前に ID 認識プロキシ／ZTNA を置き、攻撃者・端末からゲートウェイへの線を消して、経路テーブルから経路が消えることを確かめます（[露出を減らす](exposure-reduction.ja.md)）。
2. **足がかりを断つ（応答から情報を出さない）** — 応答の項目を必要最小に絞り、詳細なエラーを返さず、秘密情報を成果物に残さない。全文検索されても拾えるものが無ければ、次の一手が生まれません。
3. **連鎖のノードを潰す（横展開を止める）** — 秘密情報の集約点・長命の静的な資格情報を、短命・用途限定・送信者制約のものに置き換える。踏まれても別のコンポーネントへ届かなければ、枝は 1 ホップで止まります。

チョークポイントを 1 つ押さえるたびに「残存経路のみ」で経路テーブルを見直し、**攻撃者が次にどの経路へ向かうか**を一手先まで確かめてください。自律型は、塞いだ結果の再探索を休まず行います。

## 5. 「面倒にするだけ」の対策を見分ける

自律型の攻撃者は、**手間がかかるだけ（Tedious）の対策**を、疲れず休まず突破します。レート制限だけ・推測しにくい ID だけ・非標準ポートだけ、といった対策は、試行回数を増やせば「いつかは通る」ため、止める力ではなく時間稼ぎです。

攻撃経路のホップごとに、その根拠（発火している脅威）の対策が「面倒にするだけ」か「不可能にする」かを見分けます。一覧は [既存ガイドの §4「面倒にする／不可能にする」](ai-agent-attack-2026-10.ja.md) にあります。レート制限・監視・WAF が不要という意味ではありません。これらは**取られる量の上限と気づくまでの時間**を決める大事な対策ですが、自律型の速さに対しては、到達経路・認証・認可・保有データの設計で「通らない」ものを先に作り、その上に重ねます。

## 6. 切った経路が実機でも塞がっているかを、BAS で確かめる

図の上で経路を切っても、実機で塞がっているかは別に確かめる必要があります。攻撃経路の technique を **MITRE ATT&CK Navigator のレイヤー（JSON）**として書き出すと、
Navigator のレイヤーを取り込める BAS（侵害・攻撃シミュレーション）・CTEM・SOC のツールに、「何を模擬するか」の候補として渡せます。

### 6.1 画面から

左サイドバーの **Report** を開き、**「ATT&CK Navigator レイヤー（JSON）」**を押します。図全体の technique が出ます。
攻撃シナリオの上位経路に載る technique には「シナリオ」、チョークポイント上の脅威に由来する technique には「チョークポイント」の metadata が付きます。

### 6.2 CLI から（シナリオに絞る）

```bash
npm ci && npm run build:cli
node dist-cli/main.js export-attack-navigator model.json --node C2 --out scenario-c2.json
```

`--node` には、OBJECTIVE（攻撃目標）を設定した攻撃者ノードの ID を指定します。そのシナリオの上位経路に載るノード・エッジの脅威だけに絞られます。
省略すると画面と同じ図全体のレイヤーになります。画面と CLI は、どちらか一つで足ります。

### 6.3 使い方の例

1. チョークポイント（§4）に対策を入れる
2. そのシナリオのレイヤーを BAS に渡し、technique を模擬して、検知・遮断されることを確かめる
3. 結果を脅威パネルの「対策実装状況」に記録し、[攻撃経路分析](attack-paths.ja.md)の「残存経路のみ」で次に向かう経路を見直す

**限界：** technique は、脅威ルールの出典（references）に書かれた ATT&CK の ID から取り出しています。出典に ATT&CK の ID が無いルールは載りません。
AI 固有の脅威は ATLAS の ID になることが多く、Navigator の Enterprise 行列には出ないため、レイヤーの説明文に併記しています。網羅性は保証しません。
§2 の ATLAS の 3 つ（T0124・T0117・T0116）は攻撃者カードに由来するため、図全体のレイヤーの説明文には出ますが、`--node` で絞ったレイヤーには出ません（絞り込みの対象は経路上のノード・エッジの脅威です）。
書き出すのは模擬する technique の候補で、攻撃の手順は含みません。

---

## 7. 前提と限界

- **判定は構成図に基づきます。** 描いていない公開資産・経路は評価されません。図の質が分析の質です。
- **脆弱性の有無は分かりません。** ルールは「この経路にこの問いが立つ」ことを示すもので、実機の脆弱性を検出するものではありません（脆弱性診断・ペネトレーションテストの代わりにはなりません）。
- **検知の速さは測れません。** ログの取得・保持・送信先は入力できますが、検知と対応が攻撃の自律速度に間に合うかは、実機の訓練・テストで確かめてください。
- **件数は、あなたの図では変わります。** ここに書いたルール ID は、当てはまる図で出る候補です。

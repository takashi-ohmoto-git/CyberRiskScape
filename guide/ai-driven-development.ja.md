# AI駆動開発における Secure by Design と脅威モデリング — CyberRiskScape で何ができるか

[English](ai-driven-development.md) | **日本語**

このページは、AI が設計・実装・レビューの多くを担う開発（AI駆動開発）で、**Secure by Design と脅威モデリングを
どう続けるか**、そのために CyberRiskScape で**何ができるようになったか**を、開発の工程に沿って説明します。
個々の操作は各ガイドに任せ、このページはそれらをつなぐ地図として書いています。

Secure by Design そのものの考え方は [Secure by Design 入門](secure-by-design.ja.md) を先に読むと理解しやすくなります。

---

## 1. AI駆動開発で、脅威モデリングの何が難しくなったか

| 変化 | 脅威モデリングへの影響 |
|---|---|
| AI がコードを書く速度に、人のレビューが追いつかない | 「最初に一度だけ作図して終わり」では、図がすぐ実態とずれる |
| AI が外部 API・SaaS・MCP サーバー・エージェントのツールを気軽に足す | 信頼境界や外部インターフェースが、週単位で増える |
| 判断の記録が会話ログに散る | 「なぜこの設計にしたか」「どのリスクを受け入れたか」が後から追えない |
| AI は組織固有の前提（何を守るか・何を受け入れたか）を知らない | AI のコードやレビューが、組織にとっての重要度と食い違う |
| システムの中に AI（LLM・エージェント）が入る | プロンプトインジェクション・過剰な権限・NHI の乱立など、従来の STRIDE だけでは拾えない脅威が増える |

つまり、脅威モデルを**一度作る成果物**ではなく、**AI が読み書きし、人が判断し続ける正本**として扱う必要があります。

---

## 2. 基本の考え方 — 正本・AI・人の 3 つの役割

CyberRiskScape は、脅威モデルを次の 3 つの役割で回す前提で作られています。

| 役割 | 担うもの | CyberRiskScape での実体 |
|---|---|---|
| **正本** | 構成・脅威・判断の記録を 1 か所に保つ | 保存したプロジェクト JSON をリポジトリにコミットする。構成図・検出脅威・対応方針・リスク評価・対策実装状況が入る |
| **AI** | 正本を読み、構成の更新を提案し、差分の影響を示す | MCP サーバー（エージェントが脅威を問い合わせ、構成図を更新する）、ヘッドレス CLI（解析・差分・取り込み・書き出し） |
| **人** | 受け入れるリスク・優先順位・本番に入れるかを決める | アプリの画面（Analytics・脅威パネル）と PR のレビュー（CODEOWNERS・ブランチ保護・差分ゲート） |

**AI に任せないもの**をはっきりさせているのが特徴です。MCP サーバーから変更できるのは構成（ノード・エッジ・境界・属性・注釈）だけで、
リスクの受容・誤検知の判定・リスク評価・対策実装状況は変更できません。これらは人がアプリで記録し、PR で承認します。

## 3. 開発の工程ごとに、何ができるか

### 3.1 企画・要件 — 図が無くても脅威を調べる

| できること | 使う機能 | ガイド |
|---|---|---|
| 「LLM とベクター DB と外部ツールを使う」と決めた段階で、型ごとに当たりうる脅威をエージェントに調べさせる | MCP の `lookup_threat_rules` | [ユースケースで学ぶ MCP 連携](mcp-use-cases.ja.md) §1 |
| よくある構成から始める（AI チャットボット・Salesforce Agentforce・コンタクトセンター・NHI と ID 基盤・外部露出） | テンプレート | [テンプレートを作る・使う](templates.ja.md) |
| 何を・誰から守るかを最初に書く（システム名・目的・業務影響・セキュリティ目標、攻撃者と標的） | プロジェクト情報・攻撃者コンポーネント | [はじめての脅威モデル](first-threat-model.ja.md) |

### 3.2 設計 — AI と一緒に構成図を作り、変更の影響をその場で見る

| できること | 使う機能 | ガイド |
|---|---|---|
| エージェントに構成図を更新させ、**書く前に**脅威の増減と該当する実行トリガーを確認する | MCP の `apply_model_changes`（`dryRun`） | [ユースケースで学ぶ MCP 連携](mcp-use-cases.ja.md) §3 |
| 既存の設定から図の下書きを作る（API ゲートウェイの設定・シークレット管理のポリシー・外部露出の観測） | Kong（decK）・CyberArk（Idira）Conjur・Shodan の取り込み | [Kong AI Gateway](kong-ai-gateway.ja.md)・[NHI と ID 基盤](nhi-identity.ja.md) §6・[インターネット露出を減らす](exposure-reduction.ja.md) §4.4 |
| 図を描いた時点で脅威が出る（配置だけで出る内在的な脅威と、接続の条件で出る経路依存の脅威） | 脅威の自動検出 | [脅威パネルの読み方](reading-threats.ja.md) |

### 3.3 実装 — 脅威モデルを AI の入力にする

| できること | 使う機能 | ガイド |
|---|---|---|
| 重要な脅威を、エージェントに実装タスクへ落とさせる | MCP の `analyze_threats`・`get_threat` | [ユースケースで学ぶ MCP 連携](mcp-use-cases.ja.md) §2 |
| 脅威モデルを AI による脆弱性診断の前提情報（何を守るか・何を受け入れたか）として渡す。誤検知が減り、重大度が組織の文脈で再較正される | `THREAT_MODEL.md` 互換の Markdown 書き出し | [Security Context に変換する](security-context.ja.md) |
| コードの脆弱性診断の結果と、脅威モデルの重要脅威を突き合わせる | Snyk の MCP サーバーとの併用 | [ユースケースで学ぶ MCP 連携](mcp-use-cases.ja.md) §7 |

### 3.4 レビュー — 設計の変更を、人の判断に必ず乗せる

| できること | 使う機能 | ガイド |
|---|---|---|
| コードや IaC の PR で「脅威モデルの更新が要る変更か」を判定する（新しい信頼境界・外部インターフェース・認証・エージェントの能力拡大など T1〜T8） | 実行トリガー・GitHub Action | [AI駆動開発のCIに組み込む](ci-integration.ja.md) §3 |
| モデルの PR で、新しく出た脅威と対応方針の変更（受容・誤検知は「要承認」）を PR コメントに出し、しきい値で止める | `diff --fail-on`・SARIF | [AI駆動開発のCIに組み込む](ci-integration.ja.md) |
| エージェントが PR を出す前に、自分の変更をセルフレビューする | MCP の `diff_models` | [ユースケースで学ぶ MCP 連携](mcp-use-cases.ja.md) §4 |

### 3.5 テスト・検証 — 指摘した脅威が本当に塞がったかを確かめる

| できること | 使う機能 | ガイド |
|---|---|---|
| HTTP で確かめられる脅威（認証なし・平文・BOLA・BFLA・レート制限・プロンプトインジェクション・システムプロンプトの開示など）について、確認用のリクエストを書き出し、CI で回帰テストにする | Postman Collection の書き出し | [脅威を Postman で確かめる](postman.ja.md) |

### 3.6 評価・報告 — 優先順位を決め、判断を残し、説明する

| できること | 使う機能 | ガイド |
|---|---|---|
| 脅威ごとにリスク評価・対応方針・対策実装状況を記録する | Analytics | [Analytics でリスクを評価する](analytics-assessment.ja.md) |
| 1 つの対策が最も多くの攻撃経路に効く場所（チョークポイント）を見つける | 攻撃経路分析 | [攻撃経路分析](attack-paths.ja.md) |
| NIST CSF・NIST AI RMF・AI 事業者ガイドラインとの対応を示す | コンプライアンスマップ | [コンプライアンスマップ](compliance-map.ja.md) |
| CISO・経営層に 1 枚のサマリと上位 10 件で報告する | PDF レポート・構成図の PNG | [PDF レポートと構成図（PNG）を出力する](report-export.ja.md) |

### 3.7 運用 — 図と現実のずれを見つけ続ける

| できること | 使う機能 | ガイド |
|---|---|---|
| インターネットに出ているサービスを観測から図にし、前回との差分で新しく開いたポートを検知する | Shodan の取り込み・`diff` | [インターネット露出を減らす](exposure-reduction.ja.md) |
| 図の NHI（サービスアカウント・OAuth クライアント等）と、ID 基盤に実在するものを突き合わせる | Okta・SailPoint・CyberArk（Idira）の MCP サーバーとの併用 | [NHI と ID 基盤](nhi-identity.ja.md) §5 |

## 4. AI そのものを脅威モデル化する

AI駆動開発で作るシステムには、AI 自身が入ります。CyberRiskScape は、AI とエージェントに固有の脅威を STRIDE と並べて扱えます。

- **3 つの観点で表示を切り替えられます**：「Human Centric (STRIDE)」「AI・LLM」「Agent-Centric」。
- **出典にもとづくルール**：OWASP Top 10 for LLM Applications・OWASP Agentic Security（ASI）・MITRE ATLAS・CSA MAESTRO・
  Anthropic のゼロトラスト（AI エージェント）・OWASP Non-Human Identities Top 10 など（各ルールに出典を記載）。
- **AI の構成要素を型として描けます**：LLM・AI エージェント・サブエージェント・MCP サーバー・エージェントメモリ・ベクター DB / RAG・
  AI ゲートウェイ・ガードレール、エージェントが使う NHI（サービスアカウント・ワークロード ID・OAuth クライアント）。
- **エージェントの性質を属性で宣言できます**：自律度（Agency）・侵害時の影響範囲（Blast Radius）・ID の強度（Identity Tier）。
  未設定は最悪の値として評価するため、宣言しない限り脅威は甘く出ません。
- **経路で決まる脅威を区別します**：直接のプロンプトインジェクション（利用者 → LLM）と、外部から書き込めるデータ（Web・メール・CRM の項目など）を
  経由した間接のインジェクションは、接続の向きと相手の型で別々に検出されます。

## 5. AI と人の境界 — 何を任せ、何を任せないか

| | AI（エージェント・CI）に任せる | 人が行う |
|---|---|---|
| 構成図 | 下書き・更新の提案・取り込み（`dryRun` で影響を確認してから） | 内容が実態どおりかの確認と、適用の承認 |
| 脅威 | 列挙・差分・該当トリガーの判定・重要脅威の要約 | 重大度の評価・優先順位 |
| 判断 | — | リスクの受容・誤検知の判定・対策実装状況の記録（MCP からは変更できない） |
| 本番への反映 | 差分ゲートで止める | CODEOWNERS による承認・ブランチ保護 |

安全のための仕組みも組み込んでいます。

- **外部と通信しません。** MCP サーバーと CLI は閉域環境でも動きます。製品との連携はファイル（設定・書き出し）を読むだけで、
  製品の API を呼びません。
- **読み書きの範囲を限定します。** MCP サーバーは指定したディレクトリの中だけを扱い、人が同時に保存したファイルを上書きしないよう、
  版（`revision`）が一致しない書き込みを拒否します。
- **秘密情報を読みません。** 取り込みは構成情報（名前・種別・ホスト名など）だけを使い、認証ヘッダ・資格情報・バナー本文などを捨てます。

## 6. どこから始めるか — 段階的な導入

| 段階 | やること | 得られるもの |
|---|---|---|
| 1. 1 枚描く | テンプレートか取り込みから、対象システムの図を 1 枚作り、脅威を Analytics で評価する | 何を・誰から守るかの共通認識と、優先順位 |
| 2. 正本にする | プロジェクト JSON をリポジトリに置き、CI に差分ゲートと CODEOWNERS を入れる | 設計の変更が、必ず人の判断を通る |
| 3. AI につなぐ | MCP サーバーをコーディングエージェントに登録する | 設計中に脅威を問い合わせ、変更の影響をその場で見られる |
| 4. 周辺とつなぐ | 設定の取り込み・Postman での検証・Security Context の書き出し・Shodan による定期評価 | 設計 → 実装 → 検証 → 運用が 1 つの脅威モデルでつながる |

段階 1 だけでも価値があります。段階 2 からは、[AI駆動開発のCIに組み込む](ci-integration.ja.md)で示す
「AI駆動開発」の 4 条件（AI が複数の工程を担う手順・正本が会話ログでない・最終判断は定められた人・手順と入力してよい情報が文書化されている）を
脅威モデリングについて満たせるようになります。

## 7. 限界

- **検出される脅威は、脅威ライブラリが覆う範囲のものです。** 網羅性は保証されません。図に描かれていない構成は評価されません。
- **AI の提案と突き合わせは推定です。** エージェントによる構成図の更新、他の製品との突き合わせは、根拠を確かめて人が承認してください。
- **Secure by Design への適合を証明するものではありません。** 図と脅威の一覧は組織の取り組みの出発点で、SSDF・CRA などへの
  適合の根拠にはなりません。
- **CLI と MCP サーバーが評価するのは同梱のルールだけです。** ブラウザに保存したカスタムルールは対象外です。

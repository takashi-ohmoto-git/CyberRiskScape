# PQC 移行を支援する — 経路上で暗号が変わる箇所を洗い出す

[English](pqc-migration.md) | **日本語**

> このページの判定は、設計図（構成図）からの**推定**です。機器の設定やベンダーの回答を確かめた結果ではありません。
> 出力するレポートは簡易版であり、正規のクリプトインベントリ（暗号の利用箇所の台帳）の代わりにはなりません（§7 参照）。

PQC（Post-Quantum Cryptography：耐量子計算機暗号）への移行は、「どこでどの暗号が使われているか」を知ることから始まります。
ところが現場では、**通信が途中で暗号を解かれ、別の暗号で張り直される場所**（ロードバランサー・CDN・プロキシなど）が
見落とされがちです。このページは、そうした場所を構成図の上で洗い出し、クリプトインベントリの行の候補を作る手順を説明します。

想定する読み手は、**PQC 移行の担当になったインフラ運用担当者**です。暗号の専門知識は前提にしません。
専門用語は初出で短く説明します。

**このページの前提となる知識**：[はじめに](getting-started.ja.md)の操作（コンポーネントの配置と接続）。

---

## 1. 何ができるか

PQC 移行では、**通信の送信元から送信先まで、暗号が切れずに続く範囲（区間）ごと**に、使っている暗号を調べます。
たとえば、次のような構成です。

> 利用者のブラウザ →（TLS）→ ロードバランサー →（平文）→ Web サーバー

ロードバランサーで TLS が終端されている（暗号が解かれている）ので、これは**区間が 2 つ**に分かれます。
区間 1 は「ブラウザ〜ロードバランサー」で TLS、区間 2 は「ロードバランサー〜Web サーバー」で平文です。
区間ごとに量子コンピューターへの備えが違うため、**区間ごとに行を分けて**確認する必要があります。

CyberRiskScape の PQC 移行支援モードは、次のことをします。

- 送信元から送信先までの経路を、**暗号を終端・復号するノードで区間に分ける**
- 区間ごとに、**終端の判定**・**蓋然性**（攻撃を受けやすい場所か）・**PQC 判定**（量子耐性があるか）を出す
- 結果を**簡易レポート（CSV）**にして、クリプトインベントリの行の候補として使えるようにする

> **用語**：
> **終端**とは、そのノードで暗号が解かれ、先へは別の暗号で張り直される（または平文になる）ことです。
> **クリプトインベントリ**とは、自組織が暗号をどこでどう使っているかを一覧にした台帳です。
> **鍵交換**とは、通信の相手と暗号の鍵を安全に共有する手続きのことで、量子コンピューターに最も狙われやすい部分です。

## 2. PQC レイヤーに描く

CyberRiskScape には、深度レイヤー（L0〜L3）とは別に、**PQC レイヤー**があります。
PQC レイヤーは、暗号の終端点と経路を描くための専用の図です。

1. 左サイドバーの **Project** を開き、「深度レイヤー（L1）」のような行をクリックして展開します。
2. 一覧の下のほうにある **PQC** を選びます。区切り線の下にあり、深度レイヤーとは別系統であることを示しています。
   選ぶと、行の表示が「PQC レイヤー」に変わります。

PQC レイヤーを選んでいるときだけ、ノードとエッジのパネルに暗号の入力欄が出ます（§4）。

### 2.1 既存の図から下書きとして複製する

すでに L1 などで構成図を描いてある場合は、**ゼロから描き直さずに複製**できます。

1. 複製元にしたいレイヤー（たとえば L1）を選びます。
2. レイヤー一覧の末尾にある **このレイヤーを複製…** をクリックします。
3. 複製先（PQC）を選び、**複製する**を押します。

複製の挙動は次のとおりです。

- 複製先の中身は**丸ごと置き換わります**。複製先に要素があるときは、ダイアログに警告が出ます
- **部品番号（C3 などの ElementalID）は引き継がれます。** 深度レイヤーの C3 は、PQC レイヤーでも C3 です
- **手動の脅威・抑制（受容・誤検知）・リスク評価・対策状況は複製されません。** 図の構造と、各要素に入れた属性だけが複製されます
- 複製したあとは「元に戻す（Undo）」で取り消せます

**逆向き（PQC レイヤー → 深度レイヤー）も同じ操作**です。PQC レイヤーを選んだ状態で複製先に深度レイヤーを選びます。
PQC レイヤーで機器を足した図を、深度レイヤーの脅威分析にも使いたいときに便利です。

> 複製は**下書き**です。複製後に PQC レイヤー側で、機器の追加（§3）と暗号の情報の入力（§4）を進めてください。

## 3. 機器のステンシルを使う

経路上で暗号を扱う機器は、左サイドバーの `LIBRARY` に型として用意されています。

| 型 | カテゴリ | 暗号の扱い（既定値） |
|---|---|---|
| L2 スイッチ | Network & Edge | 透過 |
| ルーター / L3 スイッチ | Network & Edge | 透過 |
| ロードバランサー | Network & Edge | 終端（L4 動作なら透過） |
| CDN | Network & Edge | 終端 |
| VPN ゲートウェイ | Network & Edge | トンネル |
| サービスメッシュ | Network & Edge | 終端 |
| ファイアウォール | Security Controls | 透過 |
| WAF | Security Controls | 終端 |
| IDS / IPS | Security Controls | 透過 |
| プロキシ / SWG | Security Controls | 復号検査 |
| SASE / SSE | Security Controls | 復号検査 |
| ZTNA / ID 認識プロキシ | Security Controls | 終端 |
| 踏み台 | Servers | 終端 |
| HSM | Crypto & Keys | 経路上の機器ではない（鍵の保管・演算） |

ほかにも、無線アクセスポイント（トンネル）・メールゲートウェイ（終端）・プライベートエンドポイント（透過）などがあります。
カテゴリと一覧は `LIBRARY` で確認してください。

### 3.1 終端判定の 5 つの値

型ごとに、暗号の扱い方の**既定値**が決まっています。値は次の 5 つです。

| 判定 | 意味 | 区間を切るか |
|---|---|---|
| **透過** | 暗号に触れず、そのまま通す | 切らない |
| **終端** | TLS などをそのノードで終わらせ、先へは別の接続を張る | **切る** |
| **復号検査** | 暗号を解いて中身を検査し、社内 CA（自社の認証局）で証明書を作り直して先へ送る | **切る** |
| **トンネル** | 外側にトンネルを張って運ぶ。内側の暗号は変えない | 切らない（警告を出す） |
| **受動復号** | サーバーの秘密鍵を取り込み、通信を横から復号して検査する | 切らない（警告を出す） |

判定が「不明」のノードは、**安全側に倒して区間を切ります**。

> **例外**：ノードの前後のエッジがどちらも E2EE（端から端までの暗号化）のときは、内側の暗号は変わらないので区間を切りません。

### 3.2 受動復号は PQC で機能しなくなる

**受動復号**は、WAF や IDS / IPS をアウトオブバンド（通信の経路の外に置く構成）で使うときに行われます。
サーバーの秘密鍵を機器に取り込み、横から見た通信を復号します。

この方式は、**静的 RSA 鍵交換**（サーバーの固定の鍵で鍵を共有する方式）に頼っています。
TLS 1.3 では静的 RSA が廃止され、通信ごとに毎回新しい鍵を作る方式になっています。PQC の鍵交換も同様です。
そのため、**TLS 1.3 や PQC に移行すると、受動復号の機器は通信の中身を見られなくなります。**
経路に受動復号のノードがあると、区間に「受動復号」の警告が付きます。PQC 移行の阻害要因として、検査の方式を見直す必要があります。

### 3.3 クラウドの同等サービスも同じ型で描く

クラウドのサービスは、機能が同じ型で描けます。型の説明にも、対応するサービスの例を載せています。

| クラウドのサービス | 描く型 |
|---|---|
| AWS ALB / Azure Application Gateway / Google Cloud Load Balancing | ロードバランサー |
| Amazon CloudFront / Azure Front Door / Google Cloud CDN | CDN |
| AWS Transit Gateway・NAT ゲートウェイ / Azure Virtual WAN | ルーター / L3 スイッチ |
| AWS Site-to-Site VPN / Azure VPN Gateway | VPN ゲートウェイ |
| AWS PrivateLink / Azure Private Link | プライベートエンドポイント |
| AWS CloudHSM / Azure Managed HSM / Google Cloud HSM | HSM |

**専用線のサービス**（AWS Direct Connect・Azure ExpressRoute・Google Cloud Interconnect など）は機器の型ではなく、
**エッジ（接続線）の通信網の設定を「専用線 (VPN)」にして**表します。
専用線は通信事業者の設備を通るため、その区間にもクラウドとオンプレミスの間の暗号を考える必要があります。

> クラウドの機器は、暗号の設定（鍵交換の方式など）を事業者が決めていることがあります。
> その場合は、ノードの**管理主体**を「クラウド事業者」にします（§4.1）。

## 4. ノードとエッジに暗号の情報を入れる

PQC レイヤーを選んだ状態で、ノードまたはエッジを選ぶと、パネルに暗号の入力欄が出ます。
**深度レイヤーでは出ません。** すべて任意で、空のままでも分析はできます（空の項目は「要確認」として扱われます）。

### 4.1 ノード：暗号（PQC）

| 項目 | 内容 |
|---|---|
| **終端判定** | 型の既定値を上書きします。「既定（○○）」のままなら型の既定値を使います。実際の機器の構成が分かったら選びます |
| **管理主体** | 自社 / クラウド事業者。クラウド事業者を選ぶと、そのノードが区間の端になる区間に「事業者依存」の印が付きます（暗号の方式を自社で変えられない区間） |
| **署名方式** | そのノードが使う署名（証明書・コード署名など）の方式。例：`ML-DSA-65` / `ECDSA P-256` |
| **鍵の保管場所** | HSM / KMS / ソフトウェア / 不明 |
| **暗号方式の変更可否** | 機器やサービスで暗号方式を変えられるか（可 / 不可 / 不明）。変えられない機器は、移行時に交換が要ります |

終端判定のプルダウンでは、型で起こり得る別の構成（たとえばロードバランサーなら「透過」）が上位に並びます。
下には、型ごとの**確認ポイント**の説明も出ます。

### 4.2 エッジ：暗号の詳細（PQC）

| 項目 | 例 |
|---|---|
| **プロトコル** | TLS / IPsec / SSH |
| **バージョン** | 1.3 / IKEv2 |
| **鍵交換** | `X25519MLKEM768` / `ECDHE P-256` |
| **署名（証明書）** | `ML-DSA-65` / `RSA 2048` |

**鍵交換と署名**は、入力すると横に**量子耐性の判定バッジ**が出ます。

| バッジ | 意味 | 例 |
|---|---|---|
| 量子耐性あり | 量子コンピューターでも破られにくい方式 | `X25519MLKEM768`（古典方式と ML-KEM を併用するハイブリッド方式） |
| 移行中 | 標準化の前の名称など、暫定の方式 | `Kyber` |
| 量子脆弱 | 量子コンピューターで破られる公開鍵暗号 | `ECDHE` / `RSA` / `X25519` |

判定は、入力した文字列に**アルゴリズム名の部分一致**があるかで決めます。
ハイブリッド方式は複数の分類に当たるため、量子耐性ありを優先します。
どの分類にも当たらない名前は、バッジが出ません（「要確認」として扱われます）。

> エッジの暗号化（Plain / TLS / E2EE）の設定は、そのまま判定に使われます。**Plain なら、鍵交換が空でも「平文」**と判定します。

## 5. 経路を分析する

分析は、**送信元のノード**のパネルから行います。

1. PQC レイヤーで、送信元にしたいノード（たとえば利用者）を選びます。
2. パネルの **暗号経路（PQC）** で、**送信先**を選びます。
3. **経路を分析**を押します。

画面に、送信元から送信先までの**経路図**と、**区間の表**が出ます。経路が複数あるときは、**経路 1・経路 2…** のタブで切り替えます。

### 5.1 区間の見方

経路図では、暗号を終端・復号して**区間の切れ目**になったノードにはハサミのマークが付きます。
区間の表は、1 行が 1 区間です。

| 列 | 内容 |
|---|---|
| 送信元 → 送信先 | 区間の両端のノード |
| 経由 | 区間の途中で暗号に触れずに通るノード（透過・トンネル・受動復号） |
| 終端判定（根拠） | 区間の**始点**のノードの判定と、その根拠 |
| プロトコル / 鍵交換 / 署名 | 区間内のエッジに入力した値 |
| 蓋然性 | 高・中・低 |
| PQC 判定 | 区間の鍵交換の判定 |
| 署名の判定 | 区間の署名の判定 |
| 事業者依存 | 区間の両端のどちらかが、管理主体がクラウド事業者のノードである区間 |
| 警告 | 注意が要る点（§5.4） |

**終端判定の根拠**は 3 種類です。

| 根拠 | 意味 |
|---|---|
| **確定** | ノードの終端判定を、利用者が明示的に選んだ |
| **既定** | 型の既定値を使った（推定） |
| **要確認** | 型に既定値がなく、判定できない |

区間の両端が送信元・送信先そのもののときは「端点」と表示します。

### 5.2 蓋然性：攻撃を受けやすい場所か

蓋然性は、その区間が**攻撃者に近い場所**にあるかを、トラスト境界から高・中・低で判定します。そのため、**トラスト境界を先に描いておく**ことが前提です。
金融分野の情報共有組織（金融 ISAC）の FintechセキュリティWG が公表した『日本の金融機関のためのPQC移行ガイド（2025年9月版）』の考え方（高＝不特定多数から攻撃されうる／中＝外部から何らかのネットワークを介して攻撃されうる／低＝自社の内部）に倣った、簡易な判定です。

| 判定 | 条件 |
|---|---|
| **高** | 区間の端のノードがインターネット側にある、または区間のエッジの通信網が「公衆網 (Internet)」。**どのトラスト境界にも属さないノードは、インターネット側として扱われます** |
| **中** | 区間の端のノードが、パートナー（Partner）のトラスト境界の中にある |
| **低** | 上のどちらでもない（社内など） |

「**今の通信を集めて、将来量子コンピューターで解く**」攻撃は、通信を集めやすい場所ほど現実的です。
蓋然性が高い区間から先に、PQC 判定の悪いものを直すと効果的です。

### 5.3 PQC 判定：区間内の最も悪い値

区間のエッジが複数あるときは、**最も悪い値**を区間の判定にします。悪い順は次のとおりです。

**平文 → 量子脆弱 → 移行中 → 要確認 → 量子耐性あり**

署名の判定も、区間内のエッジの署名と、**区間の送信先ノードの署名方式**のうち最も悪い値です。
鍵交換や署名を何も入れていない区間は「要確認」になります。

### 5.4 警告

| 警告 | 出る条件 | 見るべき点 |
|---|---|---|
| 受動復号 | 区間の途中に受動復号のノードがある | TLS 1.3 / PQC では検査が機能しなくなる（§3.2） |
| 再署名 | 区間の始点が復号検査のノード | 社内 CA で証明書を作り直している。社内 CA の署名方式の移行が必要 |
| 外側トンネル | 区間の途中にトンネルのノードがある | 外側のトンネルの暗号が、内側の暗号を覆っている。外側の鍵交換の方式を確認する |
| 暗号の混在 | 区間内のエッジで、暗号化の設定が混在している | 区間の途中に平文と TLS が混ざっていないか確認する |

### 5.5 エッジの向きで経路が見つからないとき

経路は、まずエッジの**向きに沿って**探します。見つからなければ、**向きを無視してもう一度探し**、
「エッジの向きでは経路が見つからないため、向きを無視して探索しました」と表示します。
送信元と送信先がエッジでつながっていないときは「送信元から送信先への経路がありません」と表示されます。エッジのつなぎ忘れがないか確認してください。
経路が多すぎるときは、一部だけを表示する旨の表示が出ます。

## 6. レポートに追加して CSV を出す

分析した経路は、**レポートに追加**して、まとめて CSV に出力できます。

1. 経路の分析画面で、必要なら**レポート上のラベル**（任意）を入れ、**レポートに追加**を押します。
   ラベルを空にすると「送信元→送信先」のノード名が使われます。
2. 追加したフローは、送信元ノードのパネルの**登録済みフロー**に出ます。開き直す・削除ができます。
3. PQC レイヤーを選んだ状態で、左サイドバーの **Report** を開き、**PQC移行支援レポート（CSV）**を押します。

フローを 1 つも追加していないときは、ボタンは押せません。**CSV は PQC レイヤーを選んでいるときだけ**出力できます。
ファイル名は `pqc-migration-report-…csv` で、文字コードは UTF-8（BOM 付き）なので、表計算ソフトでそのまま開けます。

### 6.1 CSV の構成

先頭にスキーマのバージョン・プロジェクト名・システム名・フロー数・区間数・注記があり、空行のあとに表が続きます。
表は**1 行が 1 区間**です。

| 列 | 内容 |
|---|---|
| フロー | 追加したときのラベル |
| 経路 No | 経路の番号（画面の経路 1・2…） |
| 区間 No | その経路内の区間の番号（画面の表と同じ） |
| 区間の送信元 / 区間の送信先 | 部品番号とラベル（例：`C3 ロードバランサー`） |
| 経由ノード | 区間の途中のノード |
| 終端判定 | 区間の始点のノードの判定 |
| 判定根拠 | 確定 / 既定 / 要確認（事業者依存のときは付記） |
| プロトコル | 区間内のプロトコル（未入力ならエッジの暗号化区分） |
| 鍵交換 | 区間の鍵交換。未入力なら「要確認」 |
| 署名 | 区間の署名。未入力なら「要確認」 |
| 蓋然性 | 高 / 中 / 低 |
| PQC 判定 | 区間の鍵交換の判定 |
| 署名の判定 | 区間の署名の判定 |
| 警告 | §5.4 の警告と、向きを無視した探索・経路なしの注記 |

複数の経路で同じ区間が現れるときは、**最初の経路にだけ**出します。経路が見つからなかったフローは、
区間の列が空で警告だけが入った 1 行になります。

### 6.2 簡易版であることと、「要確認」の使い方

この CSV は、**設計図から推定した簡易版**です。ファイルの先頭付近にも、次の注記が入ります。

> 本レポートは設計図から推定した簡易版です。正規のクリプトインベントリは機器設定・ベンダー回答で確認してください。

CSV は、**クリプトインベントリを作るときの「行の候補」**として使います。そのうえで、

- 「判定根拠」「鍵交換」「署名」が**要確認**の行は、機器の設定を調べるか、**ベンダーに照会**する必要があります。
  **要確認の件数は、ベンダーへ問い合わせる件数の目安**になります
- 要確認が減るほど、設計図の情報が充実したことになります。ノードの終端判定やエッジの鍵交換を確かめて入力し、再度出力してください

## 7. 限界と注意

- **設計図から推定しています。** 実際の機器の設定は読みません。図が実態と違えば、判定も違います
- **型の既定値は推定です。** たとえばロードバランサーは既定で「終端」ですが、L4 で動かしていれば実際は透過です。
  ノードの終端判定を選んで上書きすると、その区間の根拠が「確定」になります
- **署名と鍵ラッピングは、経路の外の論点です。** 経路の分析は、通信の**鍵交換**を主に見ます。次の 2 つは、経路の区間では表せません。
  - **署名の偽造**（Trust Now, Forge Later：いま信頼している署名が、将来偽造される）：
    長期間使うデバイスやファームウェアの署名に関わります。ノードの**署名方式**を入れて確認し、関連する脅威ルール（長寿命デバイスの非 PQC 署名検証）で扱います
  - **鍵ラッピング**（暗号鍵を別の鍵で包んで保管すること）：長期間保管するデータが対象です。
    Storage & Databases のバックアップの型と、関連する脅威ルール（バックアップの鍵ラッピングの量子脆弱性・HSM の PQC 鍵非対応）で扱います
- **ノードごとの区間の切れ目の判定は、1 つの値です。** 同じ機器が通信の種類によって扱いを変える場合は、通信の種類ごとに別のノードに分けて描いてください

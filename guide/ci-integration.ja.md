# CI に組み込む — 脅威モデルを「正本ファイル」として扱う

[English](ci-integration.md) | **日本語**

これまでの章は、人がブラウザで脅威モデルを作図し、読み、評価する手順でした。この章は視点を変えて、
**保存したプロジェクト JSON を、リポジトリで管理する正本ファイルとして CI/CD に組み込む**方法を
説明します。ヘッドレス CLI と GitHub Action を使い、AI がコードと一緒に脅威モデルを読み書きする
開発フロー（いわゆる "AI 駆動開発"）に、脅威モデルを継続的に接続します。

この章は単独で読めますが、題材のコマンドは
[脅威モデルを AI が読める Security Context に変換する](security-context.ja.md) で説明した
エクスポート機能と並ぶ、もう一つの「ツールの外側との接続点」です。

---

## 1. 位置づけ — なぜこれが要るのか

AI がコードを書く速度に、人間のレビューが追いつかなくなりつつあります。脅威モデリングも例外では
ありません。「最初に一度だけ丁寧に作図して、あとは忘れる」という運用では、AI が毎週のように
新しい外部連携やエージェントのツールを追加する開発では、モデルはすぐに実態と乖離します。

この章が実現する "AI 駆動開発" は、次の 4 条件をすべて満たす開発のあり方を指します。

| # | 条件 | この章での実現方法 |
|---|---|---|
| 1 | 実装以外に、要件整理・設計・テスト・レビュー・ドキュメントのうち **少なくとも二つ**を AI が定常的に担う前提で手順化している | 脅威モデルの**更新**（設計）と、差分の**レビュー観点**（レビュー）を AI が定常的に扱える形にする |
| 2 | 正本は会話ログではなく、**仕様・受入条件・テスト・設計制約のいずれか**である | 保存済みプロジェクト JSON（`threat-model/project.json` 等）をリポジトリにコミットし、**設計制約の正本**として扱う |
| 3 | 採否・セキュリティ・権限・秘密情報・外部依存の**最終判断を定められた人が行い**、無審査で本番に入れない | `CODEOWNERS` とブランチ保護で、脅威モデルの変更・受容判断に**人のレビューを強制**する |
| 4 | 個人の都度の使い方ではなく、**手順・利用ツール・入力してよい情報・レビュー観点が文書化**されている | この章そのもの。手順・入力してよい情報（§6）・レビュー観点（T1〜T8）を文書化する |

つまりこの章がやることは、「脅威モデルを CI に挿すこと」自体ではなく、**脅威モデルを正本ファイルとして
人の最終判断に乗せる手順を文書化すること**です。

---

## 2. 役割分担 — AI と人

| 作業 | 担当 |
|---|---|
| コードの PR を出す／脅威モデルの更新案を作る | AI（または人） |
| モデル差分を実行し、結果を読む | AI（CI が自動実行、結果は PR コメントと AI レビュアーの両方が読める） |
| 実行トリガー（T1〜T8）チェックリストを埋める | AI（PR テンプレートに沿って該当項目にチェック） |
| 新規 Critical/High 脅威の**受容・誤検知への変更を承認する** | **人（指定レビュアー）** — CODEOWNERS で強制 |
| `threat-model-not-needed` ラベルを付与する | **人（指定レビュアー）** — 付与者は PR タイムラインに記録される |
| 採否・セキュリティ・権限・秘密情報・外部依存の最終判断 | **人** — このツールは判断材料を出すだけで、判断は代行しない |

**ゲート（CI の exit code）が強制するのは「新規の未抑制 Critical/High 脅威がないこと」だけ**です。
受容・誤検知への変更や、ラベルによるスキップは **CI では止めず**、PR 上で人の目に触れる形で記録します。
承認の強制力は Git/GitHub の記録（CODEOWNERS・ブランチ保護・PR タイムライン）に委ねます。

## 3. 二段構えの判定フロー

コードの変更すべてにモデル差分ゲートを義務付けると、無関係な PR まで毎回モデル更新を求められて
形骸化します。そこでこの章の仕組みは **二段構え**にしています。

```
            PR が立つ
                │
     ┌──────────┴──────────┐
     │                      │
モデルファイルが変更された    モデルファイルは変更されていない
     │                      │
     ↓                      ↓
② モデル差分ゲート    ① 実行トリガー判定（watch-paths）
  （本章 §4）              │
                  ┌─────────┴─────────┐
                  │                   │
         watch-paths に該当      該当しない
                  │                   │
                  ↓                   ↓
      ラベル無し→チェックリストを要求して失敗   成功
      ラベル有り→成功（付与者は記録に残る）
```

### ① 実行トリガー判定（コード・IaC・依存関係の PR）

モデルファイル自体は変わっていないが、`watch-paths`（例：`infra/**`、`**/auth/**`、
`**/package.json`、`**/Dockerfile`）に該当する変更があった PR です。脅威モデリングが
要るかどうかの判断材料として、**実行トリガー T1〜T8** のチェックリストを提示します。

| # | トリガー | 確認ポイント | モデル差分で自動判定 |
|---|---|---|---|
| T1 | 新しい信頼境界 | データが新しいネットワークセグメント、テナント分離境界、または権限境界を越える | できる |
| T2 | 新しい外部インターフェース | インターネット向け API、Webhook、gRPC エンドポイント、コールバック URL、公開 SDK | できる |
| T3 | 新しい認証／認可の仕組み | 新しいログインフロー、トークン種別、mTLS、RBAC モデル、サービス ID、証明書管理 | できる |
| T4 | 新しい技術またはランタイム | 未経験の言語、フレームワーク、データストア、クラウドサービス、デプロイモデル | **できない**（図に技術スタック情報が無い） |
| T5 | 機密データが新しい経路を通る | 顧客データ、シークレット、暗号鍵、PII が、これまで扱っていなかったコンポーネントを通過する | できる |
| T6 | 新しいサードパーティ連携 | 顧客データを受け取る、または処理する外部ベンダーの SDK、API、サービス | できる |
| T7 | エージェントの能力拡大 | 新しいツール・MCP サーバー・サブエージェントへの委譲・記憶の追加、自律性や権限の引き上げ | できる |
| T8 | モデル・学習データ・RAG ソースの変更 | 利用する LLM の変更、ファインチューニング／学習データ、RAG の参照先の追加・変更 | できる |

「モデル差分で自動判定」できるのは、**モデルファイル自体が更新された場合**の話です。
①の時点ではモデルファイルは変わっていないため、ここでは**全項目を「人／AI レビューで確認」**
として提示します（T4 がモデル差分でも自動判定できない理由は後述 §7）。

該当する変更があるのにモデルを更新していない PR は、指定レビュアーが内容を確認した上で
`threat-model-not-needed` ラベルを付けない限り、CI が失敗し続けます。

### ② モデル差分ゲート（モデルファイルの PR）

モデルファイル自体が変更された PR です。base（マージ先）版と head（PR）版を比較し、

- 該当した実行トリガー（根拠となった要素つき）
- 追加・解消された脅威
- 対応方針の変更（**受容・誤検知への変更は「要承認」**として明示）
- 実効 severity の変化
- `fail-on` によるゲート判定

を Markdown で PR コメントとジョブサマリーに出し、**新規かつ未抑制の脅威が `fail-on` 以上なら
CI を失敗**させます。既存の未対応脅威では落ちません（対応は進行中でよい）。

## 4. 導入手順

### 4.1 プロジェクト JSON をリポジトリへ保存する

アプリの **PROJECT** メニューからプロジェクト JSON をエクスポートし、リポジトリにコミットします
（例：`threat-model/project.json`）。以降、この章の仕組みは**このファイルを正本**として扱います。

### 4.2 ワークフローを追加する

[`guide/ci/threat-model.yml`](ci/threat-model.yml) を `.github/workflows/threat-model.yml` として
コピーし、`model` / `fail-on` / `watch-paths` を自分のリポジトリに合わせます。

```yaml
- uses: takashi-ohmoto-git/CyberRiskScape@main   # 本番ではコミット SHA に固定すること
  with:
    model: threat-model/project.json
    fail-on: High
    watch-paths: |
      infra/**
      **/auth/**
      **/package.json
      **/Dockerfile
```

> **本番ではブランチではなくコミット SHA に固定してください。** この Action は参照先の
> リポジトリの任意のコードを `npm ci && npm run build:cli` でビルドして実行します。
> `@main` はこのガイドでの説明用の簡略表記です。

### 4.3 CODEOWNERS を設定する

[`guide/ci/CODEOWNERS.example`](ci/CODEOWNERS.example) を参考に、モデルファイルのパスへ
指定レビュアー（チーム）を割り当てます。**ワークフローファイルと、カスタムのトリガー定義を使う
場合はそのファイルも**同じレビュアーに割り当ててください。`pull_request` で動くワークフローは
PR 側の版が使われるため、PR の中でワークフローを書き換えればゲートそのものを外せてしまいます。
（カスタムのトリガー定義は Action が base ブランチ側の版を読むので PR だけでは差し替えられませんが、
マージ後の変更にもレビューを通すために割り当てておきます。）

```
threat-model/project.json         @your-org/security-reviewers
.github/workflows/threat-model.yml  @your-org/security-reviewers
```

**`threat-model-not-needed` ラベルは CODEOWNERS では制御できません。** GitHub はラベル付与を
「triage 権限以上」単位でしか制限できないため、**ラベルを付けてよい人の範囲は社内プロセスとして
別途合意してください**（triage/write 権限の付与対象を絞る、など）。

### 4.4 ブランチ保護を設定する

対象ブランチの保護ルールで、以下を**必須**にします。

- このワークフローのステータスチェック（必須チェックとして指定）
- Code Owner のレビュー承認（§4.3 の CODEOWNERS を要求）

これにより、§2 の「無審査で本番に入れない」が技術的に担保されます。

### 4.5 PR テンプレートを置く（任意）

[`guide/ci/pull_request_template.ja.md`](ci/pull_request_template.ja.md) は
`node dist-cli/main.js triggers --format md --locale ja` の出力をベースにした、
T1〜T8 のチェックリスト付き PR テンプレートです。`.github/pull_request_template.md` として
コピーして使えます。組織独自のトリガー定義がある場合は `--triggers <file>` で差し替えて
再生成してください。

## 5. PR コメントの読み方

モデル差分ゲートが失敗（CI exit 1）した PR のコメントには、見出しごとに内容が並びます。

- **実行トリガー** — 該当した T1〜T8 と根拠要素。T4 は常に「PR レビューで確認」と表示される
- **追加された脅威／解消された脅威** — severity・対象要素・脅威名の表
- **対応方針の変更** — 「要承認」列が **Yes の行は、新たに受容または誤検知にされた脅威**。
  ここは **CI を落としません**が、指定レビュアーが内容を見て承認する前提の行です
- **実効 severity の変化**
- **ゲート判定** — `fail-on` 以上の新規未抑制脅威があれば FAIL、無ければ PASS

**「要承認」＝CI が止まっているわけではない**点に注意してください。ゲートを通っていても
「要承認」の行がある PR は、レビュアーが目を通す運用にしてください（レビュー観点として
CODEOWNERS レビューの中に組み込むのが確実です）。

## 6. 入力してよい情報

- **モデルファイルの中身は設計情報です。** 資産名・コンポーネント構成・信頼境界・認証方式などが
  含まれます。機密度の判断は**組織の情報分類に従ってください**。公開リポジトリに置く場合は、
  実在のホスト名・内部ドメイン・個人名などを含めないよう注意してください
- **CLI（`analyze` / `diff` / `triggers`）自体は外部通信を一切行いません。** 同梱の脅威ライブラリ
  のみで評価する純粋なローカル処理です
- **Action の実行には 2 種類の外部通信が発生します。** ビルド時の npm レジストリへの依存取得
  （`npm ci`）と、結果コメント投稿時の GitHub API 呼び出し（`gh pr comment`）です。閉域環境での
  回避方法は次節を参照してください
- **LLM 呼び出しはありません。** この仕組みは固定ルール（脅威ライブラリ）とモデル差分のみで
  判定します。Phase 2 で予定している LLM 連携を CI に組み込む場合は、別途明示的なオプトインに
  なります

## 7. 閉域ネットワーク・自前ランナーでの使い方

IaaS 上の自前ランナー等、npm レジストリに到達できない環境では、**Action をそのまま使わず**、
事前にビルドした CLI を直接呼び出してください。

```bash
# ビルド可能な環境で一度だけ
npm run build:cli   # dist-cli/main.js（単一ファイル、Node だけで動く）を生成

# 閉域環境では dist-cli/main.js だけを配置し、ワークフローから直接呼ぶ
node dist-cli/main.js diff base.json head.json --format md --fail-on High --out result.md
node dist-cli/main.js triggers --format md --out checklist.md
```

`dist-cli/main.js` は Node 以外の依存を持たないため、この方法なら npm レジストリにもインターネット
にも到達する必要がありません。PR コメント投稿（GitHub API 呼び出し）が必要な場合のみ、その呼び出し
先への疎通を確保してください。

---

## 8. この仕組みの限界

- **評価対象は同梱の脅威ライブラリのみです。** IndexedDB に保存するカスタムルール（ブラウザ側で
  作成したもの）は CLI からは参照できず、ファイルにも含まれません
- **T4（新しい技術またはランタイム）はモデル差分では絶対に自動判定できません。** 図に技術スタック
  の情報が無いためです。①の実行トリガー判定、またはモデル差分ゲートのコメントで常に
  「PR レビューで確認」と表示されるので、人（または AI レビュアー）が判断してください
- **LLM モデル自体の変更は検出できません。** T8 はノード追加・`rag_retrieval` エッジ追加は拾い
  ますが、同じ LLM ノードが指すモデル名の変更（例：モデルのバージョンアップ）を表す属性は
  現時点の図のデータモデルに無いため検出対象外です

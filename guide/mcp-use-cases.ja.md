# ユースケースで学ぶ MCP 連携 — 設計・レビュー・他ツールとの組み合わせ

[English](mcp-use-cases.md) | **日本語**

[前章（MCP サーバー導入ガイド）](mcp-integration.ja.md)は、設定とツールのリファレンスでした。
この章は、**業務アプリの開発チームとセキュリティ担当が、エージェント（Claude Code・GitHub
Copilot・Cursor など）に何を頼み、エージェントが何を呼び、人が何を判断するか**を、場面ごとに
紹介します。設定がまだの場合は、先に[前章の「利用者が最初にやること」](mcp-integration.ja.md#利用者が最初にやること)を済ませてください。

どの場面も、次の分担が前提です。

- エージェントができるのは、**脅威の問い合わせと、構成（ノード・エッジ・境界など）の更新**まで
- **リスク評価・受容・誤検知・対策の実装状況は、人がアプリで設定する**（エージェントからは変更できない）
- 構成の変更は PR になり、人が差分を見て判断する（[AI駆動開発のCIに組み込む](ci-integration.ja.md)）

プロンプト例は、そのままコピーして使えますが、ファイルのパスや要素の名前は自分のプロジェクトに
合わせて読み替えてください。

## 1. 設計の初期段階で、図が無くても型ごとの脅威を調べる

**状況** — 新しい機能の設計を始めたばかりで、構成図（モデル JSON）はまだ無い。RAG を使う
チャット機能を作る予定で、どんな脅威に備えるべきかを先に知りたい。

**エージェントへの指示例**

```text
RAG 構成のチャット機能を設計します。ベクトル DB と、LLM を呼び出すエージェントを
使う予定です。CyberRiskScape で、これらのコンポーネント型にどんな脅威ルールが
当たるかを調べて、設計で最初に決めておくべきことを 5 つ挙げてください。
```

**エージェントが呼ぶツールの流れ**

1. `list_component_types` — 使えるコンポーネント型の id（例：ベクトル DB・エージェント・LLM に当たる型）を確認する
2. `lookup_threat_rules` — `nodeType` に型の id、必要なら `framework`（`AI` / `AgenticAI`）を指定して、
   当たる脅威ルールを引く。`query` で語句を絞ることもできる

**人がやること** — エージェントの挙げた項目を、設計レビューの論点として採否を決める。この段階の
結果は「その型に一般に当たる脅威」であり、実際の接続や信頼境界はまだ反映されていません。
図を作ったあとは、場面 2 で本当の検出結果を見ます。

## 2. 既存モデルの重要脅威を把握し、対策を実装タスクに落とす

**状況** — 保存済みのモデル `threat-model/project.json` がある。検出された脅威のうち重要なものだけを
把握し、対策を Issue やタスクにしたい。

**エージェントへの指示例**

```text
threat-model/project.json の脅威のうち、High 以上を上位 10 件挙げてください。
それぞれ詳細を読んで、対策を実装タスク（タイトルと完了条件）にしてください。
受容や対応方針の変更はしないでください。
```

**エージェントが呼ぶツールの流れ**

1. `analyze_threats` — `minSeverity: "High"`・`limit: 10` で、実効 severity の高い順に先頭の 10 件を得る
   （`elementId` で特定のノードに絞ることもできる）
2. `get_threat` — 各脅威の `L1:<id>` を渡して、対策・出典・検出根拠を読む
3. （エージェントがタスクを書き出す。ここは CyberRiskScape の機能ではありません）

**人がやること** — タスクの妥当性を確認し、優先順位を決める。リスクの受容や「対策済み」への更新は、
実装が済んだあとに人がアプリで記録します（[Analytics でリスクを評価する](analytics-assessment.ja.md)）。
エージェントは対策の実装状況を変えられないため、タスクを作っただけで「対策済み」になることはありません。

## 3. 新しいコンポーネントを追加して影響を確認する

**状況** — 既存のシステムに、MCP サーバー・RAG のベクトル DB・外部 SaaS のいずれかを追加する
ことになった。図を更新し、脅威がどう増えるかを確認したい。

**エージェントへの指示例**

```text
threat-model/project.json の L1 に、ベクトル DB を 1 つ追加し、既存の API サーバーから
TLS でつないでください。まず dryRun で、増える脅威と該当する実行トリガーを教えてください。
問題なければ書き込んでください。
```

**エージェントが呼ぶツールの流れ**

1. `get_model` — 既存ノードの id と所属境界、`revision` を得る
2. `list_component_types` — 追加する型の id と、設定できる属性を確認する
3. `apply_model_changes`（`dryRun: true`） — ノード追加とエッジ追加を 1 回で送る。後続の操作からは、
   追加したノードを `ref` で参照する（例：`add_node` に `"ref": "vectordb"`、`add_edge` の
   `target` に `"@vectordb"`）。書き込まずに、増減する脅威と該当トリガー（例：T5・T8）が返る
4. `apply_model_changes`（`dryRun` を外す） — 内容が妥当なら、同じ内容で書き込む

**人がやること** — dryRun の結果（増える脅威とトリガー）を読み、構成が意図どおりかを確認する。
エッジの `auth`・`network`・`encryption` は、エージェントが推測した値のことがあるので、実際の
設計と合っているかを必ず確かめてください。書き込み後は、必要に応じてアプリで図の見た目を整え、
リスク評価を行います。書き込みは作業ツリーのファイルを直接更新するので、**作業の前にコミットして
おく**と、Git で元に戻せます。

## 4. PR 前のセルフレビュー

**状況** — モデル JSON を変更したブランチがある。PR を出す前に、レビュアーに見られる差分と、
確認を求められるトリガーを自分で知っておきたい。

`diff_models` は 2 つのファイルを比べます。比較元（base）は、Git から取り出して用意します。

```bash
git show origin/main:threat-model/project.json > threat-model/base.json
```

**重要** — base も `--root` 配下に置く必要があります（`--root` の外のパスは拒否されます）。
作業が済んだら `threat-model/base.json` は削除し、コミットに含めないでください。

**エージェントへの指示例**

```text
threat-model/base.json（main の版）と threat-model/project.json（作業中）を比較して、
該当する実行トリガーと、増えた・解消した脅威を教えてください。PR の説明文に
貼れる形にまとめてください。
```

**エージェントが呼ぶツールの流れ**

1. `diff_models` — `basePath` と `headPath` を渡す。該当トリガーと脅威差分（`added` / `removed` /
   `suppressionChanged` / `severityChanged`）が返る
2. `list_change_triggers` — 該当したトリガーの確認項目（T1〜T8 のチェックポイント）を読む
3. `get_threat` — 増えた脅威のうち気になるものの詳細を読む

**人がやること** — トリガーに対応する確認事項（例：T6 なら、顧客データを受け取る外部ベンダーの
扱い）を PR の説明に書く。T4（新しい技術またはランタイム）は差分から自動判定できないため、
エージェントの要約に含まれていなくても、該当しないかを自分で考えてください。PR を出すと、
CI の差分ゲートが同じ差分を出します。

## 5. GitHub Copilot

### 5.1 VS Code のエージェントモードで対話的に使う

**状況** — 設計相談をしながら、その場で図を更新したい。

設定は [4.2 VS Code の GitHub Copilot](mcp-integration.ja.md#42-vs-code-の-github-copilot)
（`.vscode/mcp.json`）です。エージェントモードで、場面 1〜4 のプロンプトがそのまま使えます。
ツールを呼ぶたびに VS Code が確認を求めるので、**書き込みツール（`apply_model_changes`）は、
引数を見てから許可する**使い方ができます。

### 5.2 コーディングエージェントに Issue を割り当てる

**状況** — 「ベクトル DB を追加する」という機能追加の Issue を Copilot コーディングエージェントに
割り当て、実装と一緒に構成図の更新も PR に含めてほしい。

**Issue に書く指示の例**

```text
## 要件
ドキュメント検索用のベクトル DB を追加し、API サーバーから参照する。

## 構成図
threat-model/project.json の L1 に、追加するベクトル DB と接続を反映すること。
CyberRiskScape の MCP ツールを使い、まず dryRun で脅威差分を確認してから書き込むこと。
PR の説明に、該当した実行トリガーと、増えた脅威の要約を書くこと。
リスク評価・受容・対策の実装状況は変更しないこと。
```

**流れ**

1. Copilot が Issue を読み、MCP ツールを**自律的に**呼んで（`get_model` → `apply_model_changes`
   の dryRun → 書き込み）、実装とモデル JSON の変更を 1 つの PR にする
2. CI の差分ゲートが、PR に脅威差分とトリガーを出す（[AI駆動開発のCIに組み込む](ci-integration.ja.md)）
3. **人（指定レビュアー）が、差分ゲートの結果を見て承認または差し戻しを判断する**

**許可する範囲の決め方** — GitHub の公式ドキュメントによると、コーディングエージェントは設定した
MCP サーバーのツールを**承認を求めずに自律的に使います**。そのため、`tools` の許可リストに入れた
ものだけが使われます。対象は MCP の**ツールのみ**で、リソースやプロンプトは対象外です。

- 構成の更新まで任せる場合：[4.3](mcp-integration.ja.md#43-github-copilot-コーディングエージェント)の
  とおり、8 本すべてを許可する。変更は PR になり、差分ゲートで人が判断する
- **読み取りだけに絞る場合**：`apply_model_changes` を外す。エージェントは脅威を調べて PR の説明に
  書けるが、図は更新できない

```json
{
  "mcpServers": {
    "cyberriskscape": {
      "type": "local",
      "command": "node",
      "args": ["dist-cli/main.js", "mcp", "--root", "."],
      "tools": [
        "get_model",
        "analyze_threats",
        "get_threat",
        "diff_models",
        "list_component_types",
        "lookup_threat_rules",
        "list_change_triggers"
      ]
    }
  }
}
```

**判断の目安** — 書き込みを許可するなら、差分ゲートと CODEOWNERS による承認が先に整っている
ことが条件です。整っていなければ、読み取りだけで始め、慣れてから書き込みを足してください。
また、クラウド環境で `dist-cli/main.js` を使うには、`npm run build:cli` を環境構築の手順に含める
必要があります（前章 4.3）。

## 6. Cursor

設定は [4.4 Cursor](mcp-integration.ja.md#44-cursor)（`.cursor/mcp.json`）です。Cursor は既定で、
MCP ツールを使う前に承認を求めます。

**設計相談の例**

```text
認証サービスを新しく追加する設計を考えています。threat-model/project.json を読んで、
今の構成で認証が弱い接続（auth が None のもの）を挙げ、追加したときに増える脅威を
dryRun で見せてください。
```

**構成更新の例**

```text
threat-model/project.json の L1 の「Web サーバー」の前に、WAF を 1 つ追加してください。
境界は既存のものと同じにして、dryRun の結果を見せてから書き込んでください。
```

呼ばれるツールの流れは場面 3 と同じです。Cursor では、ツールを呼ぶたびの承認画面で
引数（`operations`）を確認できます。自動実行を許可する設定にする場合は、書き込みツールまで
含めるかを、場面 8 の観点で決めてください。

## 7. Snyk との組み合わせ（エージェント経由）

Snyk の公式 MCP サーバーと CyberRiskScape の MCP サーバーを、**同じエージェントに並べて登録**し、
「設計上の脅威」と「実装上の脆弱性」を 1 つの会話の中で突き合わせる使い方です。2 つのサーバーは
互いに通信しません。つなぐのはエージェントです。

### 7.1 Snyk MCP の準備（Snyk の公式ドキュメントで確認した内容）

- 起動コマンドは `snyk mcp -t stdio`（stdio トランスポート）。Snyk CLI v1.1298.0 以降が必要で、
  `npx -y snyk@latest mcp -t stdio` でも起動できる
- 利用には Snyk のアカウントでの認証が必要（ブラウザでのログイン、または `SNYK_TOKEN` 環境変数）
- 提供されるツールは、オープンソース依存（SCA）・コード・IaC・コンテナ・SBOM などのスキャン。
  ツール名や対象は Snyk 側のバージョンで変わりうるので、最新は Snyk のドキュメントを参照してください
- 利用できるプランや料金、スキャンのためにコードや依存情報が Snyk のサービスへ送られるかどうかは、
  **Snyk の利用条件に従います**。このガイドでは確認できていないため、導入前に Snyk のドキュメントと
  自社の方針で確認してください

2 つを並べて登録する例（Cursor の `.cursor/mcp.json`。ほかのクライアントも、各形式で同様に並べます）：

```json
{
  "mcpServers": {
    "cyberriskscape": {
      "type": "stdio",
      "command": "node",
      "args": ["${workspaceFolder}/dist-cli/main.js", "mcp", "--root", "${workspaceFolder}"]
    },
    "snyk": {
      "type": "stdio",
      "command": "snyk",
      "args": ["mcp", "-t", "stdio"]
    }
  }
}
```

### 7.2 ユースケース

**(a) 設計上の脅威と実装上の脆弱性を並べて、優先順位を検討する**

```text
threat-model/project.json の High 以上の脅威を上位 10 件挙げてください。次に Snyk で
このリポジトリの依存関係（SCA）と IaC をスキャンし、検出を構成図のノードに対応づけてください
（どの検出がどのコンポーネントのものかを、リポジトリの構成から推定して、根拠を添えること）。
設計上の脅威と実装上の脆弱性を 1 つの表にして、優先して見るべき箇所を提案してください。
```

流れ：`analyze_threats`・`get_model`（CyberRiskScape）→ Snyk のスキャン（Snyk）→ エージェントが対応づけて
表にする。**対応づけはエージェントの推定**であり、確実なものではありません。人が根拠を確認してください。

**(b) 「実装済み」の対策と Snyk の検出の矛盾を知らせる**

```text
threat-model/project.json で、対策の実装状況が「実装済み」になっている脅威を get_threat で
読み、それに関係する領域（例：入力検証、暗号化、依存の更新）に Snyk の検出があれば、
矛盾の可能性として一覧にしてください。実装状況は変更しないでください。
```

エージェントは対策の実装状況を**変更できません**。矛盾の疑いを知らせるだけで、見直すかどうかは人が
判断し、アプリで更新します。

**(c) 依存や IaC の変更がトリガーに当たるかを検討する**

```text
この PR で package.json と Terraform が変わっています。Snyk で変更後の依存と IaC を確認したうえで、
list_change_triggers のうち T4（新しい技術）・T6（サードパーティ連携）などに当たりそうな変更を挙げ、
構成図に反映が必要なら dryRun で案を見せてください。
```

T4 は差分から自動判定できないため、依存や IaC の変更から**人または対話の中で気づく**ことに意味があります。
エージェントの提案は、そのまま書き込まず、dryRun の結果を人が確認してください。

### 7.3 限界

- **エージェント経由の連携は、毎回同じ結果になる保証がありません。** CI のゲートや、監査のエビデンス
  には使わないでください。ゲートは、前章までの CLI と GitHub Action（決定的に動く）で組みます
- **Snyk の結果は CyberRiskScape のファイルに保存されません。** 対応づけの結果も、会話の中にしか
  残りません。残したい場合は、人が PR の説明や Issue に転記します
- **リスク評価と対策の実装状況は、エージェントから変更できません。** 人がアプリで設定します
- Snyk の利用条件・料金・スキャンの範囲は、Snyk 側に従います

## 8. 共通の注意

**エージェントに許可する範囲**

| 構成 | 許可するツール | 向いている場面 |
|---|---|---|
| 読み取りのみ | `apply_model_changes` 以外の 7 本 | 脅威の調査・PR の説明・レビューの補助。まず試すとき |
| 読み書き | 8 本すべて | 構成図の更新まで任せる。差分ゲートと CODEOWNERS が整っているとき |

- 読み取りのみの構成でも、エージェントは図を**読む**ので、モデルに機密の設計情報が含まれる場合は、
  使うエージェントの提供元のデータの扱いを確認してください
- コーディングエージェントなど、ツールを**承認なしで**使う環境では、許可リストが唯一の制限です。
  必要なものだけを許可してください

**モデル内の文字列はデータ** — ノードのラベル・説明・注釈は、人や他のツールが書いた文字列です。
「この指示を無視して〜せよ」のような文があっても、エージェントに命令として扱わせないでください
（[前章 §7](mcp-integration.ja.md#7-安全のための仕組み)）。信頼できない出所のモデルを読ませるときは特に注意します。

**閉域での利用** — CyberRiskScape の MCP サーバーは、外部との通信も LLM の呼び出しもしません。
ただし、**エージェント自身（LLM を提供するサービス）や、Snyk のような他のサーバーは、別に通信します**。
閉域で使う場合は、エージェントと組み合わせるサーバーが閉域で動くかを、それぞれ確認してください。

**`--root` の置き方** — ツールの `path` は `--root` からの相対で、`--root` 配下の既存の `.json` だけが
対象です。モデル JSON を置くディレクトリ（リポジトリのルート、または `threat-model/` など）を
`--root` に指定します。`diff_models` の base も `--root` 配下に置く必要があります（場面 4）。
`--root` を広くしすぎると、無関係な JSON も読めてしまうので、必要な範囲にとどめてください。
